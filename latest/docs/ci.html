Palisade

Continuous integration

CI is defined in .github/workflows/. It runs on GitHub-hosted runners only. Self-hosted runners, third-party runner services and cloud-managed build or pipeline services are permanently prohibited: self-hosted runners on a public repository can be taken over by pull requests from forks, and paid build services have caused surprise bills. The runner-guard job enforces this on every PR (see below). If a job cannot run on a hosted runner, it becomes a documented local-only step; it is never moved to another runner type.

Branch protection requires ci-ok (and the PR title check below). It depends on every other job and fails if any of them failed, was cancelled or was skipped, so new jobs are covered without changing the branch rules. The ruleset is in repo-settings.md. Requiring the one aggregate check, instead of each job by name, is how the required set in #21 (fmt, both clippy runs, the tests, msrv, deps, docs and runner-guard), and the coverage, fuzz and bench jobs from #25, is enforced: a matrix job's check names change whenever the matrix does, and the aggregate cannot be left out of date.

The test matrix runs the whole workspace on every runner. On Linux and the other desktop OS that means the portable crates, plus the Windows-only crates as stubs; Windows x64 and Windows ARM64 run everything natively. The issue's test-portable, test-windows-x64 and test-windows-arm64 are the four entries of this one matrix.

Test reports

nextest writes a JUnit report (.config/nextest.toml, profile ci) to target/nextest/ci/junit.xml. The Test summary step runs even when the tests fail, and cargo xtask test-summary turns the report into a table on the job's summary page and one error annotation per failed test. Failure names are escaped, so a test name cannot inject a workflow command. If the tests did not build, there is no report, and the step only warns.

Coverage, fuzzing and benchmarks

Details and local commands are in testing.md.

  • coverage runs the same nextest suite instrumented by cargo-llvm-cov, and cargo xtask coverage-summary writes line, function and region coverage per crate to the job summary. It is reported, not enforced: a crate below its target (80% lines for palisade-policy and palisade-fileid) gets a warning annotation and the job still passes.

  • coverage-gate is the one coverage rule that is enforced (#25): palisade-policy line coverage must not decrease. On a pull request, cargo xtask coverage-gate runs cargo llvm-cov nextest -p palisade-policy at the PR's base commit (in a temporary git worktree) and at the PR, with PROPTEST_RNG_SEED fixed so property tests cover the same cases each time, and fails if the share of covered lines went down. Adding code at the same coverage ratio passes. Both numbers are in the job summary. Nothing is stored between runs: a baseline from main would need an artefact or a cache write from a pull request, and measuring the base again in the same job needs neither.

  • fuzz-locks runs cargo metadata --locked on each fuzz workspace (found on disk, so a new one is checked before it is listed anywhere). A pull request that changes a dependency of a crate a fuzz workspace builds, even indirectly, must re-lock that workspace; this job says so in seconds, with the minimal re-lock command (cargo metadata --manifest-path <dir>/Cargo.toml, which upgrades nothing). The fuzz job waits for it.

  • fuzz runs cargo xtask fuzz, split across a matrix of 6 shards that run in parallel. Shard I runs cargo xtask fuzz --shard I/6: the targets whose position in the list in xtask/src/fuzz.rs (in project order, counted from 0 across all projects) is I modulo 6. Together the shards run every target exactly once. Each shard builds only the projects it has a target in, each from its fuzz workspace's committed Cargo.lock, seeds each corpus from the crate's synthetic fixtures, and runs each of its targets for 60 s. A crash, hang, leak or out-of-memory input fails that shard, and so ci-ok; the shards do not cancel each other (fail-fast: false), and each shard's summary shows each failing input up to 64 KiB as base64, with the command that reproduces it.

    Shards keep each job well under its 30-minute limit as targets are added. As one job, the 17 targets took 26 minutes (1,581 s) on main: about 7 minutes building the three projects (fileid about 70 s, proto about 175 s, policy about 155 s on a hosted runner), and 60 to 85 s per target with its seeding. With 6 shards each runs at most 3 targets (18 with the bundle decoder) and builds at most two projects, about 8 minutes in all. A unit test in xtask/src/fuzz.rs reads the shard count from ci.yml and fails once a shard would get more than 5 targets; then add shards: extend the shard list and change the /6 in the job's SHARD to match (a test in xtask/src/ci.rs checks the two agree).

    The nightly toolchain is pinned by date. cargo-fuzz has no prebuilt binary in the install action, so it is built from crates.io with cargo install --locked (fallback: cargo-install, which passes no token).

  • bench builds every criterion bench and runs each benchmark once in test mode, so a bench that no longer builds or panics fails. Timings are not measured on shared runners. A unit test fails if a benches/*.rs file is not named in the job.

main-snapshot

Every push to main whose CI passed replaces the files of one rolling pre-release, tagged main-snapshot, with that commit's unsigned packages (<commit>.Palisade-<version>-x64.msi and -arm64.msi, where <commit> is the first 12 characters of the commit) and their .msi.sha256 checksums (#22). The release is marked as a pre-release, never as the latest release, and its notes say the builds are unsigned, untested snapshots and not for production use, and name the commit and the run. Every file name starts with its commit, so an upload never replaces another commit's file: the previous set stays published until the new one is complete, and is then removed, so there is only ever one set.

Only the three snapshot jobs have a write scope (contents: write, to edit the release and move the tag), and they run only on push to main, never on pull requests, so fork code never runs with it. snapshot-prepare creates the release on first use and marks it as being updated, snapshot builds and uploads each architecture's package on its own runner, and snapshot-finish checks that main still points at the commit (a re-run of an older run's job keeps that run's commit, and must not publish over a newer snapshot) and that all four files are there, then points the tag at the commit, removes older files and writes the notes. snapshot-prepare stops on any release lookup failure other than "not found", so an API error never creates a release or moves the tag. The commands are in .github/scripts/main-snapshot.sh, which uses the preinstalled gh CLI; its tests (main-snapshot.test.sh, a fake gh) run in runner-guard. Pushes to main queue rather than cancel each other (concurrency), so two snapshots never interleave.

The snapshot job builds the packages again instead of reusing the package job's: passing files between jobs needs an artefact action, and only three actions are allowed (see below). The packages are built from the same commit with the same command. Pull requests build and test the packages in package and publish nothing.

release.yml (pushed v* tags; pull requests that change release tooling)

The release pipeline: check-tag, build (x64 and ARM64, natively), server, sign (the approval-gated release-signing environment), verify, provenance and publish. Files move between jobs through a draft release, using the preinstalled gh, because no artefact action is allowed; the draft is published only after verify passes. Pull requests that change release.yml, xtask/src/dist/, xtask/src/release/ or packaging/ run only dry-run: the same build, signing with a throwaway test CA, packaging and verification, with no secrets, no write access and no upload. Details: releasing.md.

audit.yml (daily at 03:17 UTC, and on demand)

Runs cargo deny check advisories and cargo xtask audit (cargo-audit with the same ignores) against main, for the root workspace and every fuzz workspace's lockfile. Both also run on every PR (the deps job). A new advisory can affect main without any change here, which is why this is also scheduled. On failure, a second job opens an issue titled "Scheduled advisory audit is failing" with the area:security label, or comments on the open one. That job, the report jobs in fuzz.yml and links.yml, and the sync job in labels.yml are the only places with issues: write.

Dependabot (.github/dependabot.yml)

Weekly updates for Cargo dependencies (the workspace, and each fuzz workspace's own lockfile) and for the pinned action SHAs, with minor and patch bumps grouped into one PR per manifest. Security updates are opened as soon as an advisory is published. Dependabot PRs run the full CI like any other PR, including DCO, cargo-deny, cargo-audit and cargo-vet, so a bump of the root workspace merges only once the new version is audited or exempted with a note (dependencies.md). cargo-deny and cargo-audit also check each fuzz workspace's lockfile; cargo-vet covers only the root workspace, so a fuzz-only bump is reviewed in its PR. The fuzz crates are never shipped (testing.md). They are labelled area:security (Cargo) or area:infra (actions), because the label sync deletes Dependabot's default labels.

Publishing

pages.yml builds the site on every push to main (as latest) and on every release tag vX.Y.Z (as vX.Y), and pushes it to the gh-pages branch. A push made with the workflow's token does not start a Pages build, so the job then requests one through the REST API. Its write permissions, contents: write for the push and pages: write for the build request, are on that job only. It does not use the Pages deployment actions, which are not on the action allowlist; GitHub Pages serves the branch instead. One-time setting for the maintainer, in repo-settings.md.

links.yml checks every external link in the built book once a week, and opens or updates an issue when one is broken. Pull requests check internal links only (offline), so a third-party site being down never fails a PR.

Runner and action policy

cargo xtask check-workflows (the runner-guard job) checks every workflow file against allowlists in xtask/src/workflows.rs:

  • runs-on must be one of ubuntu-latest, ubuntu-24.04, windows-latest, windows-2025, windows-11-arm, macos-latest, macos-15. The only expression allowed is ${{ matrix.<key> }}, and every value of that key must be an allowed label. Matrix keys are matched case-insensitively, as GitHub does, and a matrix or include: entry built from an expression fails. Label lists, runner groups, and labels read from inputs or variables fail.
  • Every action is on the allowlist (actions/checkout, Swatinem/rust-cache, taiki-e/install-action) and pinned to a full 40-character commit SHA, with the version in a trailing comment. Container actions fail.
  • No job calls a reusable workflow (jobs.<id>.uses), local or remote. None are needed yet.
  • The workflow has a top-level permissions: block that is read-only: read-all, {}, or scopes set only to read or none. Jobs that need more ask for it themselves.
  • pull_request_target is never used, so fork PRs never run with secrets or a write token.
  • actions/checkout sets persist-credentials: false.
  • Swatinem/rust-cache sets save-if exactly once (in any letter case, as the runner matches input names), to false or to the main-branch expression, so only main writes the cache (threat model T-ci-06).
  • No file under .github/ (workflows, scripts, issue templates, anything) names a cloud-managed build or pipeline service, in any letter case, anywhere in its text or its file name. The names are kept out of this repository (NAMING.md), so the check stores only their SHA-256 digests and compares the digest of every substring of the same length.

Because the check allowlists runners and actions rather than blocklisting services, an unapproved build service fails by default. Adding a runner label or an action is a reviewed change to xtask/src/workflows.rs.

Other hardening:

  • Rust caches are written only from main (save-if, checked above), so PR builds, including forks, cannot poison them.
  • Superseded PR runs are cancelled; pushes to main always finish.
  • Every job has a timeout-minutes (30, or 60 for the test and coverage matrices and the weekly fuzz jobs).
  • CI sets CARGO_TERM_COLOR=always, CARGO_INCREMENTAL=0 and RUST_BACKTRACE=1.
  • Every Cargo command uses --locked, so CI builds exactly Cargo.lock. Tools that run Cargo themselves and have no --locked (cargo-fuzz, cargo-insta) run offline after a cargo fetch --locked, which has the same effect: the lockfile cannot be re-resolved and nothing new is downloaded.

The workspace rules the deps and feature-powerset jobs enforce are described in workspace.md.

Running the checks locally

The toolchain is pinned in rust-toolchain.toml, so rustup picks it up automatically. One command runs every check in ci.yml, with the same command lines:

cargo xtask ci          # everything, including coverage, fuzz, docs, the book, feature-powerset and msrv
cargo xtask ci --fast   # skips those slow steps, and the package, signing and server-image builds

It runs every step even after one fails, and lists the failed ones at the end. Before it starts, it checks that the extra tools are installed (cargo-nextest, cargo-deny, cargo-audit, cargo-vet, cargo-hack, typos, actionlint, zizmor and, without --fast, cargo-llvm-cov, the fuzzing nightly with cargo-fuzz, mdBook, and the MSRV toolchain), and prints the install command for each one that is missing, at the version CI uses. Jobs that differ only by runner run once, on your machine, and the fuzz job's shards run as one cargo xtask fuzz, every target once. Steps whose job runs only on one OS run only there: on Windows, ci builds both packages (the package job, without its smoke test, which installs a service); on Linux, it builds the server binary and image (the server-image job, with podman). Elsewhere they are skipped with a note, and --fast skips them. A unit test in xtask/src/ci.rs compares its steps with ci.yml, so the two cannot drift.

Not run in CI yet

Each of these arrives with the work it depends on, and runs on GitHub-hosted runners like everything else:

  • Uploading reports as artefacts (the JUnit XML, the lcov coverage report, fuzz crash inputs, the dependency report) and posting summaries as PR comments. These are not done, by policy, not by omission. Artefacts need an action outside the allowlist, and comments need a write token on pull requests, which no workflow here is given. Every one of these is in the job summary instead: test results, the coverage table and the coverage gate, fuzz findings as base64 with a reproducer, the dependency report, and the benchmark comparison.
  • The absolute performance budget of policy evaluation, with the benchmarks it is measured on (#42).
  • The vm-smoke subset of the Windows VM harness (#26).
