How to use this document

  • Threat IDs have the form T-<component>-<nn>, for example T-agent-03. They are stable: an ID is never renumbered or reused. A threat that no longer applies is marked retired in its row, with the reason, and stays in the table.
  • Code comments that implement a mitigation reference the threat: // threat: T-agent-03. Bypass scenarios in #230 list the threats they test in their threat_ids field. Coverage can then be found with git grep 'T-agent-03'.
  • Issue keys are GitHub issue numbers in this repository. A mitigation always names at least one issue that owns it.
  • Status has three values:
    • planned: the design exists (an ADR or an issue), but there is no code on main yet.
    • implemented: the code that enforces the mitigation is on main, and the verification column names an existing test, fuzz target or CI check that exercises it. When the component that will call that code is still to be built (often the agent), the row's residual-risk note says so.
    • verified: a #230 bypass scenario or a recorded red-team test shows the mitigation holding end to end on the Windows VM harness (#26). Nothing is verified yet, because the harness does not exist yet.
  • Impact and likelihood are L, M or H. Likelihood assumes the planned mitigation is absent, so it says how much the mitigation matters. Residual risk is in its own column.
  • When you change Palisade: if your change adds or moves a trust boundary, adds a parser of untrusted input, or changes how a listed mitigation works, update this document in the same pull request (see Process).

Scope

Modelled

Every Palisade component and the paths between them:

  • on the endpoint: the optional kernel driver, the agent service, the health and watchdog service, the tray notifier, the local CLI, local IPC, the protected local store (policy cache, anti-rollback record, hash cache, time state), the event buffer and the update client;
  • the OS-native policy layer that Palisade compiles and deploys (ADR 0002);
  • on the server: the agent endpoints, the REST API, the web console, the database, the signer, the certificate authorities, event ingest and outbound or inbound integrations;
  • the CI and release pipeline, from source to the agent's update client;
  • the shared policy engine and file-identity parsers, which every component relies on;
  • script and interpreter control (#7), which the interpreter bypass tree depends on.

Not modelled

  • Physical attacks that need special hardware: DMA attacks through external ports, cold-boot memory extraction, hardware implants and side channels such as speculative execution.
  • Firmware and boot-chain implants below the OS (UEFI implants, a compromised boot manager). Secure Boot is an assumption, not something Palisade enforces.
  • Vulnerabilities in Windows itself. An attacker who exploits a kernel bug is treated as the kernel-level actor in Actors and claims, and Palisade does not claim to resist them.
  • The security of the operator's own identity provider, directory, SIEM, ticketing system or hosting platform, beyond how Palisade authenticates to them.
  • High-volume denial of service against a deployment, and social engineering of the maintainer (both also out of scope in SECURITY.md).
  • Formal certification of any kind (#18 lists it as out of scope).

Assumed OS baseline

  • Endpoints: Windows 11, and Windows 10 22H2 only while it still receives security updates. Servers: Windows Server 2019 or later. x64 and ARM64.
  • Secure Boot is on. Disk encryption with the OS's built-in full-volume encryption and a TPM protector is recommended; where it is off, the residual-risk register applies.
  • The full list is in Assumptions.

Method

  • STRIDE per element. Every component has a table that considers Spoofing, Tampering, Repudiation, Information disclosure, Denial of service and Elevation of privilege. A category that does not apply is written as N/A with the reason.
  • Attack trees for the bypass techniques that are specific to application control. They use AND and OR nodes, and every leaf maps to a mitigation, an issue and a verification.
  • LINDDUN-lite for privacy threats. Its output is shared with #228 (privacy and data minimisation).
  • MITRE ATT&CK technique IDs are given for bypass trees where one fits (ATT&CK is an open framework). This answers the open question in #219: the mapping is included, at the level of attack-tree roots, and #230 scenarios may carry the same IDs in their technique field.

Three design decisions shape the whole model:

  1. The native layer keeps enforcing without the agent (ADR 0002, ADR 0012). Stopping or crashing the agent removes reporting and the driver-only rules, not the baseline policy.
  2. Everything the agent trusts is signed end to end (ADR 0005, ADR 0008): policy bundles, commands, unlock tokens, trust sets and updates. The transport is protected too, but trust never depends on it.
  3. Decisions never wait for the network (ADR 0009). Slowing or blocking the server cannot hang or loosen enforcement.

Bypass attack trees

Each tree has a goal at the root. OR means any child achieves the parent. AND means every child is needed, so blocking any one of them defeats the parent. Each leaf ends with → and its mitigation, the owning issue, the threat ID and the verification.

Verification IDs:

  • BYP-* are bypass scenarios for the #230 suite (tests/bypass/);
  • FUZZ-* are #230 fuzz targets;
  • RT-* are entries in the #230 red-team checklist, for techniques that cannot be automated safely;
  • TEST-* are unit or integration tests owned by the named issue;
  • TEST: followed by a test name is a test that already exists on main;
  • fuzz: followed by a name is a cargo-fuzz target that already exists on main;
  • CI: followed by a command is a check that already runs in CI.

The BYP, FUZZ, RT and TEST-* names are proposals. #230 fixes the final names.

In the verification column, entries are separated by ;, and each entry that points at something on main starts with its tag:

  • TEST: then the crate in backticks and one or more test paths in backticks, for example TEST: `palisade-policy` `tests::allow_rules_need_a_strong_positive_identity` . A later crate name in backticks switches the crate. The last segment of a path is the test function's name.
  • fuzz: then one or more fuzz target names in backticks.
  • CI: then the command in backticks, as a workflow under .github/workflows/ runs it.

Assumptions

  1. Secure Boot is on on every endpoint, and the boot configuration does not allow test-signed or unsigned drivers outside disposable lab VMs.
  2. Disk encryption with a TPM protector is recommended on every endpoint. Where it is off, R-05 applies in full.
  3. Administrative accounts are separate from everyday accounts and are not used for email or web browsing, in line with ISM-1175-style guidance. Standard users do not hold local administrator rights (#160, #161).
  4. The OS is supported and patched. Kernel vulnerabilities in the OS itself are not mitigated by Palisade.
  5. Hypervisor-enforced code integrity is recommended where hardware supports it. It reduces R-02 but is not required.
  6. Time: endpoints and the server use a reliable time source. The server keeps its offset under 1 s (#224); its clock health check (clock.ntp_servers) reports clock_offset in readiness when it is not.
  7. TLS inspection is bypassed for the agent endpoints. Palisade never disables verification to work with an inspecting proxy (ADR 0005).
  8. The server is run by trusted operators on a hardened host or container (#229), with the database owner role and signer credentials kept off the runtime host.
  9. Root keys stay offline: the root CA and the update metadata root are used only in documented ceremonies (#224, #226).
  10. GitHub-hosted runners are the only CI runners (docs/ci.md), and the hosting platform's own controls (branch rules, environments, attestations) work as documented.
  11. Testing happens on disposable VMs first (ADR 0014).

Process

Review cadence

The model is reviewed, and the header's "Last reviewed" date updated:

  • at every minor release;
  • whenever a new component or trust boundary is added;
  • whenever a mitigation's status changes from planned;
  • and at least every 6 months.

Each review is a changelog entry that says what changed and who reviewed it.

Keeping it current

  • A pull request that changes a trust boundary or adds a parser of untrusted input updates this document. The pull request template asks this question.
  • New threats get the next free number for their component. IDs are never reused.
  • A mitigation moves from planned to implemented in the pull request that lands it, with the test name in the verification column.
  • cargo xtask threat-coverage runs in the doc-checks CI job, behind the required ci-ok check, so it is blocking. It fails when:
    • a STRIDE row is malformed (cell count, ID form, category, status, impact or likelihood), an ID is reused, an N/A row has no reason, or a component does not consider all six categories;
    • the mitigation table lacks a row for a threat, has one twice or out of order, or names different issues from the STRIDE row;
    • a threat marked implemented or verified has no TEST:, fuzz: or CI: entry, or a verified threat has no BYP-* or RT-* entry;
    • any TEST:, fuzz: or CI: entry, on any row, names a test function, fuzz target or workflow command that does not exist;
    • the summary by status does not match the tables;
    • this document or a tracked .rs or .md file names a threat ID the tables do not define, such as a // threat: comment with a wrong number.
  • What it cannot check: that a cited test really exercises the mitigation. Reviewers check that, and #230 turns the proposed BYP-* and RT-* names into scenarios.

Disclosure

Vulnerability reports go through GitHub private vulnerability reporting, as described in SECURITY.md, which also has the supported-versions table. Private reporting is enabled on the repository (docs/repo-settings.md). A finding is in scope when it defeats a claim in Actors and claims. It is out of scope when it needs an actor this model says Palisade does not resist.
