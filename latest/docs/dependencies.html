Dependencies and supply chain

Third-party crates make up most of the code that Palisade's privileged Windows service trusts. A compromised or careless dependency can do anything the service can do. This page says how a dependency gets in, and what checks it on every pull request. CI runs all of them (ci.md), and cargo xtask ci runs them locally.

Admitting a new dependency

Every new top-level dependency is justified in the pull request description. Say why it is needed, and cover each of these:

CriterionWhat to check
NeedIs it worth it? A small piece of code may be better written in the crate that needs it.
MaintenanceRecent releases, open issues and pull requests, more than one maintainer, a security policy.
UseDownloads and reverse dependencies. Widely used crates are reviewed more, by more people.
unsafeHow much it has, and whether it is documented. cargo xtask deps-report counts it.
FootprintHow many crates it pulls in, on every platform. cargo tree -p <crate> --target all -e normal.
LicenceOne of the licences allowed in deny.toml.
Build-time codeBuild scripts and proc-macros run on the build machine. They must not use the network; prefer crates with none.
FeaturesUse default-features = false and turn on only the features needed, so less code is compiled.

Add the version once, in [workspace.dependencies] in the root Cargo.toml, and use { workspace = true } in the crate (cargo xtask check-manifests). The allowed directions between workspace crates are in workspace.md.

Keep the agent's tree small. The agent runs as a privileged service and should pull in much less than the server. The dependency report lists each crate's tree size separately. In the agent, prefer windows-sys to windows: it is bindings only, so it compiles faster and ships less.

What runs on every pull request

CheckToolEnforces
LockfileCargoCargo.lock is committed, and every Cargo command uses --locked.
Licencescargo deny check licensesOnly the licences in deny.toml (Apache-2.0, MIT, BSD-2/3-Clause, ISC, Unicode-3.0, Zlib, CC0-1.0, MPL-2.0), plus the exceptions listed there with a reason. GPL, AGPL and LGPL fail unless an exception with a reason is added. confidence-threshold = 0.9.

Auditscargo vet --lockedEvery crate is audited, covered by an imported audit, or exempted with a note (below).
Repository rulescargo xtask check-supply-chainAt most 10 crates in more than one version. Every advisory ignore has an ID, a reason and an expiry date that has not passed, and no audit.toml exists. Every skip has a reason, and every licence exception a # reason: comment. The cargo-vet criteria for each workspace crate, no [policy] entry that lowers what dependencies need, and a note on every exemption.
Reportcargo xtask deps-reportOn a PR that changes Cargo.lock, the job summary shows duplicates, cargo tree -d, third-party crates per workspace crate, every third-party crate's unsafe count with the change against the base branch, and the build scripts and proc-macros. A new crate with more than 100 unsafe keywords, or a version that adds more than 100 compared with the version it replaces, raises a warning on the run. The old counts come from the base commit: the report checks it out in a temporary git worktree and runs cargo metadata --locked there, which downloads and unpacks its locked crates.io packages (checksum-verified; nothing is built). If that fails, the change is shown without a warning rather than raising a false one.

The fuzz targets (crates/*/fuzz) are separate workspaces with their own Cargo.lock. The licence, source, ban and advisory checks run on them too, with this same deny.toml, and cargo xtask audit scans their lockfiles. Their one licence exception is NCSA for libfuzzer-sys (LLVM's permissive licence), which the root workspace does not use, so cargo deny check there warns that the exception is unused. cargo-vet covers only the root workspace; fuzz crates are never shipped, and a fuzz-only dependency is reviewed in its PR (testing.md).

Advisories are also scanned daily (audit.yml), because a new advisory can affect main without any change here. A failure opens or updates an issue labelled area:security.

To see the checks fail, add a GPL-licensed crate, a git = "..." dependency, or a crate from another registry: cargo deny check rejects each one.

Ignoring an advisory

Only when the vulnerable code cannot be reached, and only for a limited time. Add a table to [advisories] ignore in deny.toml:

ignore = [
    { id = "RUSTSEC-2026-0001", reason = "only the parser is used, not the affected writer", expiry = "2027-01-31" },
]

expiry is cargo-deny's own key: it fails the advisory check once the date has passed. cargo xtask check-supply-chain also fails then, and requires the ID, the reason and the date on every entry. Review the advisory again, and renew the date with a new reason or remove the ignore.

deny.toml is the only place an advisory is ignored. CI runs cargo-audit as cargo xtask audit, which passes the same IDs as --ignore, so both tools agree. A cargo-audit audit.toml anywhere in the repository fails check-supply-chain, because it would bypass these rules.

An ignore has exactly these three keys. cargo-deny also accepts allow, which limits an ignore to some dependents, but cargo-audit cannot scope an ignore, so allow is rejected to keep the two tools in step. cargo xtask audit runs these checks before cargo-audit, so an expired or incomplete ignore also fails the daily audit.

A licence exception works the same way, except that cargo-deny has no reason key for it: write a # reason: ... comment on the line directly above each entry in [licenses] exceptions, in the inline-array or the [[licenses.exceptions]] form. Each entry needs its own comment.

cargo-vet

supply-chain/ holds the cargo-vet files:

  • config.toml: the criteria and exemptions. Product crates, which are shipped, require safe-to-deploy for their whole tree. xtask and dev-dependencies require safe-to-run.
  • audits.toml: audits done for this project.
  • imports.lock: the audits imported from trusted public audit sets, pinned.

Audits are imported from two public sets run by non-profit open-source organisations. When cargo-vet was adopted, 6 crates were covered by imported audits, and the other 93 were recorded as exemptions with the note "Baseline when cargo-vet was adopted". The 17 crates that the Authenticode verifier (#247) brought in while cargo-vet was in review (ring and its build and platform dependencies) are exempted the same way, with a note that names #247. Identity matching (#251) added 2 more (unicode-normalization and tinyvec), exempted with a note that names #251. It also made regex-automata, regex-syntax and aho-corasick normal dependencies of palisade-policy, so their baseline exemptions were raised from safe-to-run to safe-to-deploy, with a note saying so. The agent service host (#252) added 16 more (the async runtime, logging and the Windows service crates), exempted with a note that names #252, and made bitflags and once_cell normal dependencies of a shipped crate, so their baseline exemptions were raised to safe-to-deploy the same way. The server's Postgres layer (#127) added 72 more (sqlx with its Postgres driver, migration support and the rustls-based TLS with the OS trust store), exempted with a note that names #127, and raised 31 baseline exemptions (syn, url, the Unicode and ICU crates and their helpers) to safe-to-deploy the same way. App package identity (#53) added 2 more (miniz_oxide, raw DEFLATE for package members, and its checksum crate adler2), exempted with a note that names #53. Dependabot PRs #308 (proptest, sha2) and #309 (criterion 0.8) were merged before cargo vet passed; the follow-up moved their exemptions to the new versions and exempted the 6 crates they added (core_detect, and for criterion alloca, page_size and winapi with its two import-library crates), all dev-only except sha2, with a note that names the PR. X.509 issuance for the internal CA (#224) added 8 more (rcgen, used without its cryptography back end, and time, yasna and their helpers), behind palisade-proto's off-by-default issuance feature, exempted with a note that names #224. The exemptions are the backlog. Each one is removed when the crate is audited, or when an imported audit covers it (cargo vet prune removes exemptions that are no longer needed).

A new crate, or a version bump, fails cargo vet until one of these is done:

  1. An imported audit covers it. Run cargo vet to see.
  2. You audit it. Run cargo vet diff <crate> <old> <new> (or cargo vet inspect for a new crate), read the code against the criteria, then run cargo vet certify.
  3. It is exempted. Only with a reason. Run cargo vet add-exemption <crate> <version>, then add a notes field to the entry in config.toml saying why it was not audited. check-supply-chain fails on an exemption without notes.

cargo vet suggest lists the cheapest audits to do next.

Code that runs at build time

Build scripts (build.rs) and proc-macros run on the developer's or CI machine during the build, with that machine's permissions. cargo xtask deps-report lists every one. Review the list when a pull request adds one. The aim for the agent's tree is that no build script touches the network.
