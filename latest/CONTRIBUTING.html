Palisade

Contributing to Palisade

Thanks for your interest. Palisade is an educational, personal-development project with one maintainer. It is not a replacement for commercial application control products. Contributions are welcome, and are reviewed on a best-effort basis (see SUPPORT.md).

By taking part you agree to follow the Code of Conduct and the responsible-use statement.

Security vulnerabilities, including bypasses, are never reported in issues or pull requests. Use SECURITY.md.

Before you start

  • For anything larger than a small fix, comment on the issue first, or open one, so the work is not duplicated and the design is agreed before you write code.
  • Decisions that affect several crates, the security model, or what is blocked or allowed need an ADR (see Architecture decisions).

How issues are organised

  • Epics are issues labelled epic (#1 to #18). Each covers one area of the project.
  • Every other issue names its parent epic at the top (**Parent epic:** #N), and often the issues it depends on (**Depends on:** #N).
  • Every issue belongs to one milestone, from M0 Foundations to M6 Compliance & Advanced. Milestones are delivered roughly in order.
  • area:* labels say which part of the project an issue touches, and priority:p0 to priority:p2 give its priority within the milestone.
  • good first issue and help wanted mark issues that suit new contributors.
  • New issues get needs-triage. The maintainer replaces it with area and priority labels. blocked marks an issue that waits on another issue or a decision.
  • The label set and the milestone titles are kept in .github/labels.yml and .github/milestones.yml, and a workflow syncs them to GitHub. To add or change a label, edit the file in a pull request (docs/repo-settings.md).

A pull request says which issue it relates to: Closes #N if it completes the issue, or Part of #N if it delivers part of it. Say what is left and which issue it belongs to.

Development setup

You need rustup and Git. The toolchain is pinned in rust-toolchain.toml, so the first cargo command in the repository installs the right version, components and targets.

  • Windows: rustup's installer offers to install the Windows C++ build tools that the x86_64-pc-windows-msvc and aarch64-pc-windows-msvc targets need. Accept that.
  • Linux and other desktop OS: no extra system packages are needed today. Windows-only crates build as stubs, so the whole workspace builds and tests anywhere.
  • cargo-deny (for the dependency check): cargo install cargo-deny --version 0.22.0 --locked.

To check Windows-only code from Linux or another desktop OS:

rustup target add x86_64-pc-windows-gnu
cargo check --workspace --all-targets --target x86_64-pc-windows-gnu

Fuller guides: docs/dev/windows.md (build tools, running the agent in the foreground, tracing, test signing in a VM, and what to do if a policy locks you out) and docs/dev/unix.md (what builds where, the dev container, running the server, and the fake agent for server and console work without Windows).

Git hooks (opt-in)

.githooks/ has a pre-commit hook (formatting, spelling and banned terms) and a commit-msg hook (the Conventional Commit format below). They are off until you turn them on for your clone:

git config core.hooksPath .githooks

Nothing in the repository turns them on for you. git commit --no-verify skips them once; CI runs the same checks either way. See .githooks/README.md.

Before you push

Run the same checks CI runs. docs/ci.md explains each one, and how to install the few extra tools.

cargo xtask ci          # every check in ci.yml
cargo xtask ci --fast   # skips coverage, fuzz, docs, feature-powerset, msrv and the package builds

Coding standards

The lints live in [workspace.lints] in the root Cargo.toml, and every crate inherits them (cargo xtask check-manifests enforces that). CI runs clippy with -D warnings, so every warning fails CI, including the lints set to warn.

Errors and panics

  • No unwrap() or expect() in non-test code. clippy::unwrap_used is denied, and clippy::expect_used warns, which fails CI. Tests may use both (clippy.toml).
  • Return errors with enough context to act on. Do not panic on bad input: Palisade parses untrusted files, policy and network messages.
  • todo!(), unimplemented!() and dbg!() are denied.

Time, processes and the platform

  • Read the OS only through the palisade_core::platform traits (#29), so the logic can be tested on any OS with the mocks in palisade_core::test_util.
  • clippy.toml bans std::time::SystemTime::now everywhere: take time from a palisade_core::platform::Clock. The one implementation that reads the wall clock, and repository tooling, say so with #[expect(clippy::disallowed_methods, reason = "...")].
  • palisade-policy also bans std::process::Command::new, in its tests too (crates/palisade-policy/clippy.toml). Clippy reads the nearest clippy.toml, so a setting added to the root file must be added to that one as well.
  • Formatting is cargo fmt with the stable options in rustfmt.toml. .editorconfig sets the editor defaults that match it.
  • Silent numeric truncation is flagged (cast_possible_truncation and related lints). Use checked conversions.
  • Public items need doc comments (missing_docs).

Unsafe code

  • Today unsafe_code is forbid for the whole workspace, so no crate may contain unsafe.
  • When unsafe code is allowed is decided in ADR 0011. In short: unsafe only in a few named FFI modules and the driver, and every file that allows it listed in unsafe-allowlist.txt, which needs maintainer review. cargo xtask check-unsafe checks that the allowlist matches the code (docs/workspace.md).
  • Every unsafe block needs a // SAFETY: comment that explains why it is sound. Clippy's undocumented_unsafe_blocks lint is already denied.

Naming

Docs, code, comments, commit messages and PR text must not name commercial products, vendors or their trademarked feature names. Use the neutral terms in docs/NAMING.md. Operating system components and open standards are fine to name.

Licence headers

Source files do not carry licence headers. The licence is declared once, as the SPDX expression Apache-2.0 OR MIT, in [workspace.package], and every crate inherits it (cargo xtask check-manifests enforces that). Files copied from elsewhere keep their original notices.

Third-party notices

Release artefacts ship the licence texts of every third-party crate they contain, in a THIRD_PARTY_NOTICES.md file generated from Cargo.lock at release time. It is not kept in the repository, because it would go stale with every dependency update. Generating it, and including it in the release archives and the installer, is part of the release pipeline (#24) and MSI packaging (#22). The licences it may contain are limited by the allowlist in deny.toml.

Testing expectations

  • Every change that affects behaviour comes with tests. Bug fixes include a test that fails without the fix.
  • New rule types or condition types need property tests (for example: a rule never matches a file it should not) and snapshot tests of their compiled or serialised form.
  • Every parser of untrusted input needs a fuzz target, listed in xtask/src/fuzz.rs so CI runs it (docs/testing.md). If a parser's target is not ready yet, say in your PR that it is still owed.
  • Test names, determinism (no sleeps, no network), platform gating and fixtures follow docs/testing.md.
  • Test files must be benign (responsible use). Never commit real malware.
  • Code that only runs on Windows is gated with #[cfg(windows)], so the workspace still builds and tests on other platforms.

Dependencies

Every third-party dependency becomes part of the code a privileged Windows service trusts, so new ones are added with care.

  • Add the version once, in [workspace.dependencies] in the root Cargo.toml, and use { workspace = true } in the crate. cargo xtask check-manifests enforces this.
  • Justify every new dependency in the PR description: why it is needed, what it pulls in, and its licence and maintenance status.
  • cargo deny --locked check must pass: allowed licences only, crates.io only, no known advisories (deny.toml).
  • The allowed dependency directions between workspace crates are enforced by cargo xtask check-deps.

The full admission policy, cargo-vet audits and the other supply-chain checks are in docs/dependencies.md.

Architecture decisions

Significant decisions are recorded as Architecture Decision Records (ADRs) in docs/adr/. PROCESS.md says when a change needs an ADR, and how to write, number, accept and supersede one, starting from the template. If you are not sure whether your change needs one, ask in the issue. If a PR contradicts an accepted ADR, it must link a new ADR that supersedes it. cargo xtask adr new "<title>" starts one from the template, cargo xtask adr index updates the index, and cargo xtask adr lint checks the format, as CI does.

Commits and pull requests

Conventional Commits

Commit messages and PR titles follow Conventional Commits:

<type>(<optional scope>): <summary>
  • Types: feat, fix, security, docs, ci, build, refactor, test, chore, and revert for reverting an earlier change.
  • Scope: a crate name without the palisade- prefix (core, fileid, policy, agent, server, cli and so on) or an area (adr, deps, xtask). Lowercase letters, digits and -, . or _.
  • Add ! before the colon for a breaking change, for example feat(policy)!: ….
  • Examples: feat(policy): add publisher rule condition, fix(agent): handle renamed files, docs: explain rule precedence.

Pull requests are squash-merged, and the PR title becomes the commit message on main, which the release changelog is generated from (cargo xtask release prepare, docs/releasing.md). The PR title check (.github/workflows/pr-title.yml) fails a pull request whose title does not follow this format. Edit the title to fix it; the check reruns.

Sign-off and licensing of contributions

There is no Contributor Licence Agreement. Contributions are accepted under the project licence, inbound = outbound (ADR 0010): unless you explicitly state otherwise, any contribution you intentionally submit for inclusion in Palisade, as defined in the Apache-2.0 licence, is dual-licensed as Apache-2.0 OR MIT, without any additional terms or conditions.

Sign-off

Sign off every commit with the Developer Certificate of Origin (DCO). Signing off says that you wrote the change, or otherwise have the right to submit it under the project licence. Add the sign-off with git commit -s, which appends a trailer with the name and email from your Git configuration:

Signed-off-by: Ada Lovelace <ada@example.org>
  • The email in the trailer must match the commit's author email.
  • To sign off commits you have already made, run git rebase --signoff <base branch> and then git push --force-with-lease.
  • Never sign off on someone else's behalf.

Maintainer exemption. Pull requests opened by the repository owner's account do not need sign-off, and the DCO check passes them with a notice. The owner holds the copyright and the right to license their own changes, so a sign-off adds nothing. This also covers changes prepared by AI coding agents working for the owner: the owner authorises each one by opening and merging the pull request from their own account, and agents never add a Signed-off-by: line in the owner's name. The exemption is decided by GitHub's record of who opened the pull request (author_association is OWNER), not by anything in the commits, so it cannot be claimed by copying the owner's name or email. Everyone else, including collaborators, signs off as above. The exemption covers every commit in an owner-opened pull request, so if the owner carries someone else's commit, the owner checks that commit's sign-off by hand.

The DCO check (.github/workflows/dco.yml) reports every commit in a pull request that has no matching sign-off. It is informational for now. The decision to require sign-off, with no CLA, is recorded in a separate ADR under #28. Once that ADR is accepted, the maintainer makes DCO a required check (docs/repo-settings.md).

Squash merges turn a pull request into one commit on main. The DCO check covers the commits in the pull request, and the pull request keeps them on record, so the squashed commit on main is not checked again.

Pull request size

  • One concern per pull request. Refactoring, formatting and behaviour changes go in separate PRs.
  • Aim for under about 400 changed lines, not counting generated files, lockfiles and test fixtures. Split larger work into a series of PRs that each build, pass CI and make sense on their own.
  • Fill in the pull request template. It is the reviewer's checklist.

Review

  • The ci-ok check and the PR title check must pass. The main branch ruleset makes both required (docs/repo-settings.md). The DCO check must pass too, although it is not yet a required check. It passes pull requests opened by the repository owner (see Sign-off).
  • Changes to CI, supply-chain policy, unsafe code, the driver and signing need the maintainer's review (.github/CODEOWNERS).
  • Workflow changes must pass cargo xtask check-workflows: GitHub-hosted runners only, allowlisted actions pinned to a full commit SHA, and read-only default permissions. Self-hosted runners and cloud-managed build services are never allowed (docs/ci.md).
