Source
Expand description

The canonical event schema (#196).

Every endpoint decision, agent health signal and policy change that Palisade records is one Event: a common envelope plus the field sets that its EventType needs. Every output, the server store and alert rules consume this one structure. Outputs are pure encoders, so a field means the same thing everywhere.

The event types and their rules are data, in crates/palisade-proto/events/registry.yaml. That file is the source of EventType (generated into registry_gen.rs) and of the reference table crates/palisade-proto/events/REGISTRY.md. The registry unit tests fail when either generated file is stale.

The JSON Schema is generated from these types (schema) and committed at schemas/events/v1.json.

§Schema versioning and compatibility

Every event carries schema_version, MAJOR.MINOR.PATCH. Writers always write CURRENT.

  • Patch: documentation only. No event changes.
  • Minor: additive. A minor version may add optional fields, field sets, event types, enum values (a category, an outcome, a source kind), and mapping entries. It never adds a required field, never makes an optional field required, and never changes what an existing field means.
  • Major: anything else. Renaming or removing a field, changing its type or meaning, or changing an existing event type’s category or required field sets. A major version gets a new schema file (schemas/events/v2.json) and a converter.

Each addition records the version it arrived in: the registry has a since for every event type, FieldSet::since gives it for every field set, and Event::min_version is the oldest version an event can be labelled with. An event labelled with an older version than a part it uses is invalid (EventErrorCode::NewerThanVersion), in Event::validate and in the JSON Schema alike, so a version label always tells a reader which fields it may meet.

Version history:

  • 1.0.0: the envelope; the process, file, script, native and agent field sets; the execution-control, policy and agent types.
  • 1.1.0: the network, device, registry, elevation, approval, admin, identity, audit_policy, restriction, probe and fim field sets; the containment, device, storage, network, web, elevation, approval, exception, override, admin, identity, detection, integrity, compliance, process-creation and script-logging types; source.kind third_party with source.format. New fields come after every 1.0 field, so the canonical form of a 1.0 event is unchanged.
  • 1.2.0: the policy integrity types of #225 (policy.signature.invalid, policy.rollback_rejected, policy.target_mismatch, policy.stale, policy.lkg_loaded, policy.emergency_loaded, policy.schema_unsupported and tamper.policy.rollback_suspected). No fields change.
  • 1.3.0: policy.kid, the key that signed the policy bundle (#325), so policy.applied names its signing key. It comes after every older policy field, so the canonical form of an older event is unchanged.

Readers are strict. They reject unknown fields and unknown enum values, because events are hash-chained (seq, prev_hash) and a reader that silently dropped a field it did not know would hide data from the chain’s verifier. A reader accepts events of its own major version and a minor version no newer than its own (Event::from_json). A newer minor version is refused with LoadError::NewerMinorVersion rather than read with fields missing. So the deployment rule is: upgrade the server before the agents. Down-converting events for older external consumers is the server’s job when it exports them (#198, #202).

§The hash chain

seq is the producer’s monotonic sequence number and prev_hash the chain value of the producer’s previous event. The first event of a chain has seq 0 and no prev_hash; every later event has one. How the chain value is computed (a keyed MAC over Event::to_canonical_json) and how the chain head is reported belong to #220 and #202.

The schema cannot make the chain complete. As the threat model records (T-events-03), events after the last reported chain head can be deleted and the local sequence rolled back without a gap the server can see. The chain only proves that events the server has seen were not altered or reordered. Shorter upload intervals and uploading tamper events first (#197) narrow that window.
