palisade_proto::pki

Module issue 

Source
Expand description

X.509 issuance for the internal CA hierarchy (#224). Only with the issuance feature, which the server and the offline ceremony tool enable and the agent does not.

The hierarchy:

root-ca (offline, self-signed, pathLen 1)
  └── issuing-ca (online, pathLen 0)
        ├── device certificate   clientAuth            CN = device ID, URNs for device and tenant
        ├── relay certificate    serverAuth, clientAuth DNS names, URNs for relay and tenant
        └── server certificate   serverAuth            DNS names

A new root is introduced by cross-signing: the old root signs a certificate for the new root’s name and key (CaCertificate::cross_signed), so a chain that ends in the new root also builds to the old one while agents still pin it. Revocation lists (revocation_list) are signed by the CA whose certificates they list: the root lists revoked issuing CAs, and an issuing CA lists revoked leaves.

Every certificate key is ECDSA P-384 and every signature is ECDSA P-384 with SHA-384 (ADR 0017). rcgen only encodes: it is built without a cryptography back end, and every signature comes from a Signer through Signer::sign_x509, which only root-ca and issuing-ca keys may use.

Each certificate gets a random 16-byte serial from the operating system’s secure random source. Times are whole seconds: X.509 has no smaller unit, so each bound is rounded down, and the Validity returned is the one written. A child never outlives its issuer, and a device certificate lives at most MAX_DEVICE_LIFETIME_DAYS days (#223).

Key identifiers (subjectKeyIdentifier and authorityKeyIdentifier) are the first 20 bytes of the SHA-256 of the DER SubjectPublicKeyInfo, the same digest the Kid takes its first 16 bytes from.

Not here yet: loading a stored CA certificate back (the ceremony CLI, #15), recording issuance in the audit log (T-ca-04, #132), and the mTLS handshake that checks device certificates (#223).
