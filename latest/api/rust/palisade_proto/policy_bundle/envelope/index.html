palisade_proto::policy_bundle

The signed policy bundle envelope (#325): signing on the server, and the agent’s verification, which produces the Examined that select decides on.

§Format

One canonical, strict, versioned binary encoding, in the style of the trust-set envelope (crate::pki::trust_set). All integers are big-endian.

envelope = version:u8 (= 1)
           kind:u8 (1 = bundle, 2 = delta)
           payload_len:u32 (1..=limit) payload
           n_sigs:u8 (1..=8) sig * n_sigs        ascending kid, no repeats
sig      = kid:[u8;16] alg:u8 bytes:[u8; length fixed by alg]

alg is SignatureAlgorithm::code: ecdsa-p384-sha384 (the default) or ed25519 (ADR 0008, ADR 0017). More than one signature lets a bundle carry signatures from an old and a new key during a rotation (#224). Nothing may follow the last signature, and the decoder refuses anything Envelope::encode would not write, so encode(decode(b)) == b.

§What is signed

Every signature covers Domain::Policy’s prefix followed by the canonical bundle bytes: "palisade-policy-v1\0" ‖ bundle_bytes.

  • For kind = 1, the payload is that bundle.
  • For kind = 2, the payload is a [BundleDelta], and the signatures cover the result bundle the delta produces, not the delta. The agent rebuilds the full bundle from its verified base with rebuild, which yields an ordinary bundle envelope, and verifies that. A delta is never trusted on its own, so an unsigned or forged delta can at most produce bytes that fail verification. The rebuilt envelope is what the policy cache stores (#326), so the stored bundle always carries its own signatures.

Only bundle bytes are ever signed in the policy domain, and every bundle starts with the CBOR array byte 0x82, so one signed message can never be read as another kind of thing.

§Header fields are not repeated

The envelope does not repeat the tenant, target, policy_version or any other header field. The agent reads them only from the signed bundle bytes, with [decode_header], so there is no unsigned copy that could disagree with the signed one.

§Verification order

verify runs #225’s checks in order, and fails closed on every error:

  1. the envelope size limit (64 MiB of bundle by default), before any byte is read, then the strict envelope decoding;
  2. at least one valid signature from a key the trust set lists for policy signing, inside its validity window. Signatures from keys the trust set does not list are ignored, so a bundle can be signed for agents on both sides of a rotation; a signature from a listed key that names an algorithm the trust set does not accept or that is not the key’s, or that does not verify, is tampering and fails the bundle even if another signature verifies;
  3. tenant and target, and 4. the version: these depend on the device’s enrolment and anti-rollback record, so select::pending and select::startup apply them to the Examined this returns, in this order (policy_bundle::check);
  4. min_agent_version;
  5. the schema: the header’s format and schema version, and, for a bundle whose signature verified, the strict [PolicyBundle::decode] of the body.

The header is read with [decode_header], which reads nothing past the header. The body is decoded only after a signature verifies, or when the effective signature mode (audit or warn) loads bundles whose signature fails anyway. In enforce mode a bundle without a valid signature is never decoded, and its schema is reported as unsupported: a check that did not run never counts as passed (ADR 0018). The signature check refuses it first in any case.
