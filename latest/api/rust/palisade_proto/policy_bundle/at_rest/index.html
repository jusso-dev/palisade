Policy cache files at rest (#326): AES-256-GCM sealing under a data key, with the nonce and seal-count rules of ADR 0017.

The agent seals each cache file (a signed bundle envelope, #325) before writing it, and opens it after reading. Sealing adds confidentiality and an integrity check, but it never replaces signature verification: the opened bytes are the signed envelope, which the agent verifies as if it had never been sealed. A file that does not open is unreadable, never trusted.

§Formats

All integers are big-endian.

sealed  = "PLCS" version:u8 (= 1) key_id:[u8;16] nonce:[u8;12] ciphertext tag:[u8;16]
keyring = "PLKR" version:u8 (= 1) seals:u64 key_id:[u8;16] key:[u8;32]
          retired:u8 (0 or 1) [key_id:[u8;16] key:[u8;32]]

A sealed file’s additional authenticated data is "palisade-policy-cache-v1\0" followed by its first 21 bytes (magic, version and key ID), so the key ID cannot be changed without failing the tag.

§Keys and nonces (ADR 0017)

KeyRing holds the current data key and, after a rotation, the one before it (to open files sealed before the rotation). Every nonce is drawn from the OS secure random source inside KeyRing::seal; no caller can pass one. A key seals at most KeyRing::SEAL_LIMIT (2^32) messages, which keeps the chance of any repeated nonce under one key at or below 2^-33. The count is persisted before a seal is used: KeyRing::reserve raises it (rotating first if the key is used up), the caller persists KeyRing::encode, and only then does KeyRing::seal use the reservation. A keyring that is missing or does not decode is never repaired: the caller generates a new one, which “rotates now”.

The keyring holds raw keys, so the agent protects it before writing it (machine-scope DPAPI on Windows). ring does not wipe key memory on drop; the agent process is trusted with the keys for its life.
