The clock health check (#224, ISM-0988).

Certificate, token and trust-set validity all depend on the server’s clock. Every clock.check_interval_secs the server asks the configured NTP servers for the time over SNTP (palisade_proto::sntp), in order, and uses the first valid reply. Health then reports:

  • nothing, when the offset is at most clock.max_offset_ms (1 s by default);
  • clock_offset (status degraded, still ready) when it is larger, with a warning in the log;
  • clock_unknown (status degraded, still ready) when no server gave a valid reply, so an unmeasured clock is never reported as good.

The check only reports. It never steps or slews the clock: that is the operating system’s NTP client’s job. A bad clock degrades rather than fails readiness, because taking every listener out of service would strand agents for a problem the server cannot fix by itself.

Without clock.ntp_servers the check does not run and health carries no clock indicator; serve logs that the clock is unmonitored.
