Precedence models: choosing one rule from the rules that match (#35, ADR 0004).

A policy names one PrecedenceModel and its PrecedenceOptions. The model only decides among the ordinary rules of stage 4 of the pipeline in crate::evaluate: the rules that allow, allow_contained, allow_elevated or deny outside a mandatory rule set. The mandatory deny tier and exclusions are decided before it, under every model, and the implicit deny after it.

Each model is a Precedence implementation: a pure function from a MatchSet to a Resolution. It reads nothing but the candidates’ metadata, so it is deterministic. Every key ends with the rule ID, which is unique, so no two candidates ever compare equal, and the winner never depends on the order of the match set. The rule-order models (first_match, priority) depend on order and priority by design, but not on where a rule or rule set sits in a list.

§The models

  • deny_wins (the default): if any candidate denies, a deny decides; otherwise an allow does.
  • allow_wins: if any candidate allows, an allow decides; otherwise a deny does. With granularity_tiebreak, the candidates of each rule set are first narrowed to that set’s most specific ones, so a denied file inside an allowed folder of the same set stays denied. Validation warns that allow_wins is not recommended for Essential Eight.
  • specificity: the candidate with the most specific identity (Spec) decides. Between equally specific candidates, a deny beats an allow unless same_tier_tiebreak: allow.
  • first_match: candidates are sorted by order, lowest first. Ties go to the newer rule, which is the higher rule ID because rule IDs are UUIDv7, whose leading bits are the creation time; IDs created in the same millisecond fall back to the rest of the ID. With curated_first (the default), rules of read-only (curated) rule sets come before every custom rule. In an effective policy built from a hierarchy (#37), each rule set carries the band of the level that assigned it, and a lower band comes before everything else, so the levels are evaluated in their configured order. defer, audit and trust_source rules are never candidates, so a matching defer falls through to the next rule.
  • priority: the lowest priority number decides (priority_direction: higher_wins reverses this). Between equal priorities: deny, then allow_contained, allow, allow_elevated with condition: always, and allow_elevated with if_required last.

A rule the model needs a position or priority for, but that has none, sorts after every rule that has one. Validation rejects such rules (order_required, priority_required).

§Ties between candidates of the same kind

In deny_wins, allow_wins and specificity, several allows can qualify. allow_tiebreak picks among them: most_restrictive (the default) prefers allow_contained, then allow, then allow_elevated with always, then with if_required; most_permissive is the reverse. Several denies, or allows of the same kind, are then ranked by specificity, and finally by the lowest rule ID, the oldest rule. That decides which rule’s directives and effects (notification, severity, kill_running) the decision carries; every other candidate is listed as overridden.
