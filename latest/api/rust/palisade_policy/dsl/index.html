The YAML policy language (#190): human-authored YAML over the same model and JSON Schema as the JSON form.

A YAML policy file holds the same PolicyDocument as the JSON form, with the same field names, and the JSON Schema in schemas/policy/v1.json validates both. JSON text is also accepted, since it is a subset of YAML.

use palisade_policy::dsl;

let yaml = "\
schema_version: 1.0.0
policy:
  id: 01936b2e-8c4a-7b3d-9f21-0a1b2c3d4e5f
  name: Example
  revision: 1
  mode: audit
";
let loaded = dsl::from_str(yaml).unwrap();
assert_eq!(loaded.document().policy.name, "Example");
let written = dsl::to_string(loaded.document()).unwrap();
assert_eq!(dsl::from_str(&written).unwrap().document(), loaded.document());

§Reading untrusted input

Reading is strict, so a file means the same thing to every tool that reads it, and hostile input cannot exhaust memory or the stack:

  • YAML 1.2 only. A %YAML directive for another version, %TAG and reserved directives are rejected.
  • No anchors, aliases, tags or merge keys (&a, *a, !t, <<). Without aliases a document cannot expand (“billion laughs”), and without tags no value is typed by a directive in the file.
  • Duplicate keys are an error, in every map, including keys that are only spelled differently (a and "a").
  • Unknown fields are an error, as in the JSON form.
  • No implicit type changes between YAML versions. A plain (unquoted) scalar is typed once, by the rules below, and a scalar that YAML 1.1 and YAML 1.2 readers type differently is an error that asks for quotes. So country: NO (the “Norway problem”: a boolean in YAML 1.1) and version: 010 (octal in YAML 1.1) are rejected rather than misread.
  • Plain scalars are never converted to the field’s type. revision: "1" and values: [1.0] are type errors, as they are in JSON: a field that wants text needs text, and the error says to quote the value.
  • No characters outside the YAML 1.2 printable set, and no raw U+0085, U+2028 or U+2029, which YAML 1.1 reads as line breaks. All of them can be written as escapes in double-quoted strings. The whole input is checked for these before anything is parsed, and the first one is reported before any other problem. That cannot be done per document, because the parser stops silently at U+0000 as if the input ended there; so in a stream, such a character in a later document is reported ahead of a model error in an earlier one.
  • Limits on input size, nesting depth, node count and parser lookahead (Limits), so memory use is bounded by the input size and the node count, and stack use by the depth.

Plain scalars are typed as follows: null, Null, NULL, ~ and the empty scalar are null; true and false (also True, TRUE, False, FALSE) are booleans; JSON numbers are numbers (integers if they have no fraction or exponent); yes, no, on, off, y, n in any of their YAML 1.1 spellings, and numbers in non-JSON forms (+1, 010, 0x1f, 0o17, 1_000, .5, 1., .inf, .nan, and YAML 1.1 base-60 such as 1:30), are errors; anything else is text (1:60 is not base-60). That includes dotted versions (1.0.0) and dates (2027-06-30): the YAML 1.2 core schema has no timestamp type, and the model has no date or floating-point fields, so a reader that typed these differently would fail schema validation rather than silently read another value. The writer quotes them anyway. Quoted and block scalars are always text.

§Writing

to_string writes canonical block-style YAML: fields in schema order, a 2-space indent, and a yaml-language-server header that names the schema. Strings are quoted unless every YAML 1.1 and 1.2 reader reads them back as the same text (so versions and dates are quoted), and characters that are not printable, or that some readers treat as line breaks, are escaped. Floating-point numbers are never written, because the model has none.

§Diagnostics

Every error carries a 1-based line and column, where the column counts Unicode scalar values (an input that is too large has no location). Load errors (YamlError) also carry the JSON Pointer of the value when one is known. Validation findings keep their stable ErrorCode and JSON Pointer, and YamlDocument::validate adds the location of the value they point to, for errors and warnings alike.

§JSON input

An input that is a valid JSON object or array is read by a streaming JSON tokenizer rather than the YAML parser. It gives the same tree, through the same limits and strictness rules (duplicate keys, typing, locations), and the same meaning, since JSON is a subset of YAML 1.2. It also reads what the YAML parser gets wrong or slowly: surrogate-pair escapes ("\uD83D\uDEE1"), a tab after :, and large documents, which the YAML parser would read whole before reporting their first value (see Limits::max_lookahead). Text that is not valid JSON is read as YAML.
