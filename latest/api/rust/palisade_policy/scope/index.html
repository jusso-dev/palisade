Rule scoping: who, where and when a rule applies (#38).

A Scope narrows a rule to some users and groups (principals), devices (devices), network locations (network), sessions (sessions) and times (schedule). Scopes are attached at three levels: a Rule’s own scope, the scopes of a rule set’s assignment to the policy (RuleSetScope), and the policy’s scope. They intersect down the chain: a rule applies only when its match tree matches and every scope on the way to it matches.

§Scopes are not match trees

The match tree identifies the object; a scope says where that rule is in force. They are kept apart on purpose. A rule’s tree must always have a positive identity (#33, the identity-anchor rule), and context criteria never count as one. A scope holds only context (who, where, when), so a “user is in Users and the session is RDP” filter belongs in a scope and never makes a tree valid on its own. A scope is also never part of a rule’s specificity (#35): it decides whether a rule is a candidate, and the precedence model then chooses among the candidates as before.

§Evaluation

A scope evaluates to a Tri, with the Kleene logic of crate::condition:

  • Each dimension that is set is an include and an exclude list. An empty include means everyone or everything. A match in exclude always wins: the dimension is include AND NOT exclude.
  • combine: all (the default) is the AND of the dimensions that are set, and combine: any their OR. A scope with no dimension is Match.
  • negate: true applies the rule when the scope does not match.

The rule then applies when scope AND tree is Match, so an out-of-scope rule behaves exactly as if it were absent: it never decides, and it is not listed as overridden. Unknown follows the rule’s action, as an unknown tree does: an allow, trust source or exclusion never applies (it fails closed), and a deny applies only with unknown_as: match. Because a scope is only ever ANDed in, it can narrow a rule but never widen it.

§Restrictive readings

Some facts have two readings, and the engine takes the one that is safer for the rule’s action. A rule permits when it lets an object run, trusts it or excludes it (ActionKind::needs_identity); every other rule (deny, audit) restricts. A position in a scope is positive when a match there makes the rule apply more: an include of a scope without negate, or an exclude of one with it.

  • Deny-only groups. UAC marks the administrator groups of a filtered token deny-only. Such a group may be read as membership or as none, and the scopes of a rule are evaluated both ways. A permitting rule takes the reading that makes it apply less, and a restricting rule the one that makes it apply more (deny_only_group). So a non-elevated administrator never gets an administrators-only allow, is never let off a deny that excludes administrators, and an administrators-only deny still applies to them. Each reading is consistent, so an exclude that holds the include still never matches.
  • Clock integrity. If the agent’s trusted time (#18) is missing or flagged, or the time zone a schedule needs is unknown, a schedule reads as whatever keeps a permitting rule inactive and a restricting rule active, so scheduled allows go inactive and scheduled denies stay in force (clock_untrusted).
  • Names. user_pattern matches the DOMAIN\user name, which can be spoofed more easily than a SID. Validation only accepts it in a position where matching it makes the rules it covers apply less if they permit, or more if they restrict, so a spoofed name can never gain anything. That rules it out of allow includes. Audit rules take it anywhere.

§Group membership

Principals are tested against the subject’s access token (ScopeFacts::process_token by default; see ScopeSubject). A token’s group SIDs already include nested directory groups and local groups, and a membership test is a binary search over them. Cloud-directory groups are not in the token: the agent caches them with cached_at. A cached membership older than the policy’s group_cache_max_age_secs (default 24 hours), cached in the future, or read while the clock is untrusted is Unknown (scope_stale).

§Schedules

See schedule. Windows may wrap midnight, and daylight-saving changes follow one rule (the “compatible” rule of the ECMAScript Temporal proposal): a local time that occurs twice means its first occurrence, and a local time skipped by a change is moved forward by the length of the change.

§Facts

The facts are in EvaluationContext: the user, device, session and network context, and the facts only scopes read (ScopeFacts). As everywhere in this crate, the agent collects them (#4), and a fact that was not collected is unknown.
