Rule lifecycle (#40): when a rule is active, which rules are exceptions, review dates, expiry notices, review campaigns and bulk changes. Everything here is pure: the caller supplies the time.

§Active rules and the clock

A rule is active when it is enabled, activates_at (if set) has been reached, and expires_at (if set) has not. An inactive rule behaves exactly as if it were absent: it never decides, annotates or grants (Evaluator::at). The decision trace (#41) reports it as inactive with Activity’s reason.

Activity is checked against a RuleClock: the agent’s time now, its floor (the lower bound on real time that the agent keeps in protected storage and never lowers), and whether the agent is anchored (ADR 0012, ADR 0018). While the agent is anchored, now is anchored time and the floor is raised to it, so the two agree. An offline-started agent (after a restart, before its next check-in) has only the wall clock for now, which anyone who can change the clock controls.

While the agent is offline-started, a time-bounded rule that lets an object run, trusts it or excludes it (ActionKind::needs_identity) is inactive, whatever the readings say: grants from the policy bundle do not start or continue until the next check-in (ADR 0018, rule 2). It is reported as expired once the floor has passed its expiry, and as not_yet_active otherwise. This is the same result as with no clock at all (activity_at). Every other rule, and every rule while anchored, is judged from the two readings, each in the closed direction:

  • A rule that lets an object run, trusts it or excludes it (ActionKind::needs_identity) is active only while both readings are inside its window. It has expired once either reading reaches expires_at, and the floor never goes back, so an expired allow never revives after a clock rollback. It activates only once both readings reach activates_at, so setting the clock forwards cannot start it early.
  • A deny, audit or defer rule is active while either reading is inside its window: it activates once either reaches activates_at, and expires only once both reach expires_at. Setting the clock forwards cannot end a deny early.

With on_expire: convert_to_audit an expired rule becomes an audit rule instead of absent: it records matches but never decides. delete_after_days behaves as absent at once, and retire_due lists it for deletion once the days have passed.

§Exceptions

An exception (is_exception) is a rule that weakens the default-deny posture by its nature: an ignore, an allow whose path identity is in a user-writable location (#31), an allow with a weak identity (file name, metadata, or SHA-1 or MD5 only), or any rule with metadata.exception: true. In governance mode an exception needs approved_at, expires_at at most 365 days after it, justification, approved_by and risk_rating (crate::validate, exception_* codes). The year counts from approved_at only (exception_start): only a renewal in a review (ReviewAction::Renew) moves it, so an attestation or a bulk extension never stretches an exception past a year from its approval.

bulk

effective_action
What the rule does in an evaluation at clock: its own action, an audit (an expired rule with on_expire: convert_to_audit), or nothing.
exception_limit
The latest expiry an exception may have: 365 days after its approval, counted from no later than now when a time is known, so an approval dated in the future cannot stretch it. None without approved_at.
exception_start
When an exception’s year starts: its approval, approved_at. Neither created_at nor last_reviewed_at counts, so a creation date written in the future or an attestation cannot stretch it. Only a renewal in a review (ReviewAction::Renew) re-approves an exception and so moves its start.
expiry_notices
The expiry notices due in (since, until], for every rule of the policy’s referenced rule sets with an expires_at. The server calls this on a schedule with the previous run’s until as since, so each notice is sent once. Sorted by due time, then rule.
inactive_matches
The rules that would have matched subject but are inactive at clock, with why, sorted by rule ID: what the decision trace (#41) reports as “would have matched disabled rule R” or “expired rule R”. Not for the hot path: it compiles each inactive rule’s tree.
is_exception
Whether rule is an exception by its nature or by its metadata (see the module documentation).
needs_review

retire_due
The expired rules whose on_expire: delete_after_days has passed at now: the server deletes them in a change set. Sorted.
review
