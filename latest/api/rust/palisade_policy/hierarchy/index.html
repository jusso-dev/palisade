Module hierarchy 

Source
Expand description

The group hierarchy, inheritance and the effective policy of a device (#37).

A HierarchyDocument is one snapshot of an installation’s scopes: the tree of nodes, the policies assigned to them, the reusable libraries and the automatic placement rules. It is an immutable value. HierarchyDocument::validate checks it once and returns a ValidatedHierarchy, from which ValidatedHierarchy::effective_policy computes the one effective policy of a device. That is a pure function of the snapshot, the libraries at their resolved versions, and the device’s membership of dynamic groups. The same inputs always give the same policy and the same content hash, whatever order the snapshot lists anything in.

The server stores the snapshot, computes and caches effective policies (#10, #127, #128, #129), and ships them in the bundle (#43). The agent only ever sees the flattened result.

Each tenant has the built-in groups unassigned (exactly one: new and unmapped devices; its mode is audit unless it sets one), and at most one each of unmanaged (removed from management: the effective policy is Management::Unmanaged, and the agent goes to disabled with tamper protection released) and staging (hidden: no device can be in it, and placement cannot target it; it is for dry runs with ValidatedHierarchy::effective_policy_as). Built-in groups sit directly below their tenant and have no child groups. Every reference to a node is checked, and a parent cycle is rejected with its path (node_cycle).

§Layers

A device’s effective policy is built from layers, from the outermost to the nearest: the global node, its tenant, its groups from the tenant down, its dynamic groups (the highest rank first, so the lowest rank is nearest), and the device. A node that links to a template is preceded by the template’s layer at the same position. Within one node, policies are applied by slot_order: the lowest slot wins a conflict.

§Rules are additive

A node contributes the rule sets of every policy assigned to it, the rule set libraries it assigns (rule_sets), and every rule set library in each of its categories, including ones added later. The effective rule list is the union over all layers. Each rule keeps its provenance: the nodes that contributed it and how (RuleProvenance). A rule set that two layers contribute is included once. Two different rule sets with one ID, including two versions of one library, are rejected (rule_set_conflict, library_version_conflict), so a child cannot pin an older version of an inherited blocklist.

A child cannot delete an inherited rule. It can:

  • suppress it locally, with suppress_inherited: [rule_id], if the rule set allows it: allow_child_suppress, which defaults to true for allowlists and baselines and to false for every other kind, so blocklists cannot be suppressed unless they say so. A mandatory rule set can never be suppressed, whatever it says (ADR 0004, #125). A suppressed rule stays in the effective policy, disabled, and its provenance says which node suppressed it. A suppression only applies to a rule that every contributing layer is above the suppressing node; if the node or a nearer layer also contributes the rule set, the rule stays active and is reported as reasserted; or
  • shadow it with a rule of its own that wins under the precedence model. Mandatory denies are evaluated before every model, so nothing shadows them.

§Settings are override-by-nearest

Each top-level key of PolicySettings is one setting. A layer sets a key through its node’s settings map, or through an assigned policy whose value for the key differs from the default; to set a key back to its default below a node that changed it, use the node’s settings. A node’s own settings beat the policies assigned to it. The nearest layer that sets a key wins. A key in a node’s locked_settings keeps the value it has at that node (after the node’s own layers) for every layer below; a later attempt to change it is ignored and reported (blocked_by_lock). Settings added to the model later are inherited the same way, with no change here.

The mode options are merged the same way, per key: mode_by_type.<type>, mode_disconnected and disconnected_after_secs. locked_settings may lock them too, as mode_options.mode_disconnected, mode_options.disconnected_after_secs and mode_options.mode_by_type (every type at once). A mode_disconnected that is not at least as strict as the effective mode is dropped, because unset means the effective mode itself.

§Modes

Each layer’s mode is its node’s mode, or else the mode of its policies, merged by mode_merge: closest (the default) takes the policy with the lowest slot, strictest the strictest (#36). The built-in unassigned group is audit unless it sets a mode. Across layers, closest takes the nearest layer’s mode and strictest the strictest of all. With no mode anywhere the device is in audit (ADR 0012).

A node with lock_mode: true fixes a floor: the mode in force at that node. Nothing in the effective policy may then decide in a weaker mode: a weaker effective mode, mode_by_type entry or rule set mode_override is raised to the floor, a control level that would cap below it is raised (an enforce floor needs enforce, an audit or learning floor at least audit), and with an enforce floor never_enforce rules become inherit. A lock applies to the whole effective policy, including what the locking node assigns itself. Every change is listed in ModeProvenance::adjustments. Raising is always allowed below a lock.

§Precedence models

The model is chosen by the nearest of the global node and the tenant that sets precedence; a group may set it only if its tenant’s tenant_options.allow_group_precedence is true (precedence_not_allowed). With no node choosing, the model of the highest-ranked policy (nearest layer, lowest slot) applies. Every policy in the effective policy must use exactly that model and its options, or the effective policy is rejected (precedence_conflict), so one effective policy never mixes models.

§First-match bands

Under first_match, rules are ordered by level before their order: every rule set carries the band of the first layer that contributed it (RuleSet::band). level_order: top_down (the default) puts the global node first, then the tenant, the groups from the tenant down, the dynamic groups and the device, so a local administrator cannot pre-empt global policy; bottom_up reverses that; flat puts every rule set in band 0, so only order counts. Mandatory denies and exclusions are decided before the model in every case, and the implicit deny after it.

§Templates

A node may be created from a template in two ways. A one-time copy (ValidatedHierarchy::copy_from_template) copies the template’s assignments, rule sets, categories, settings, mode and suppressions into a new node, with no link afterwards. A linked node sets template: the template’s layer is applied at the node’s position, just before the node’s own, on every computation, so later changes to the template take effect. A template cannot link to another template.

§Explaining

EffectivePolicy::rule and EffectivePolicy::setting return, for a rule or a setting, every node that contributed it, how, and whether it was suppressed, reasserted, overridden or blocked by a lock (for #41).

§Placement

Each tenant has an ordered list of placement rules (placement), see placement.
