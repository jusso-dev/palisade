§palisade-policy

The policy model, conditions, precedence and evaluation, with a decision trace. Evaluation is pure and deterministic: no network or filesystem access.

Status: the policy object model, its JSON Schema and validation are in place (#30), with a YAML front end (#190). Single criteria can be matched against an object’s facts (#31, #32), and whole match trees can be evaluated, with context criteria for the user, device, session, network and time (#33). Rule actions, effect flags and the typed Decision are defined (#34). The evaluation pipeline and the five precedence models turn the matching rules into one decision (#35). Enforcement modes, their resolution per decision and the mode state machine are in place (#36). The group hierarchy, inheritance, reusable libraries and the effective policy of a device are in place (#37). Rules, rule-set assignments and policies can be scoped by user, group, device, network location, session and time (#38). Rules have activity windows, governance metadata, hit counters and review queries, and the policy assistant lints a policy (#40). Every decision can be traced, explained and simulated (#41). Rule indexes, the lazy fact protocol, the decision cache and the performance budget are in place (#42). The unknown-application policy decides what happens when no rule does, with the built-in system_baseline, Palisade’s self-allow and the Essential Eight presets (#39). Work is tracked in #2.

§Modules

  • model: the canonical policy object model. A PolicyDocument holds one Policy and the RuleSets it references by ID. Each rule has a match tree (all / any / not / criterion) and an action. Strict serde: unknown fields are rejected, and enums are snake_case strings.
  • schema: generates the JSON Schema (draft 2020-12) from the model. The generated schema is committed at schemas/policy/v1.json.
  • migrate: migrations between major versions of the schema (#330). Each Step is a pure function that rewrites a document of major N as major N + 1; migrate applies them in order and leaves a current document unchanged, so it is idempotent. read_json reads a document of any supported major (rejecting repeated keys), migrates it and reads the result in strict mode, so a migration can never make an unknown field or criterion acceptable. v0, the pre-release draft model, kept schema_version in policy and called a rule’s effects flags. Fixtures for each old version are in tests/fixtures/migrate/.
  • lenient: the lenient reader for agents that receive a newer minor version (#330). read_json migrates an older major first, then sets aside only what can never relax a decision: unknown or unreadable fields of metadata and governance, and unreadable rules whose action is audit, defer, trust_source or ignore. Each is returned in ignored with its JSON Pointer and value. Any other unknown field, and an unreadable allow, deny, allow_contained or allow_elevated rule, or a rule with an unknown action, refuses the whole document, so the device keeps the policy it has (ADR 0018). Strict reading (PolicyDocument::from_json) stays the default and the mode for authoring.
  • dsl: reads and writes policy documents as YAML. The YAML form has the same fields as the JSON form, and the same JSON Schema validates both. Reading is strict and safe on untrusted input: YAML 1.2 only, no anchors, aliases, tags or merge keys, no duplicate keys or unknown fields, no scalar that YAML 1.1 and 1.2 type differently (such as no or 010), and limits on size, depth, node count and parser lookahead. JSON input is read by a streaming JSON reader that builds the same tree under the same rules. Errors and warnings carry a line and column. Examples are in docs/examples/policies/.
  • validate: PolicyDocument::validate reports every finding in one pass. Each finding has a stable code, a severity and the JSON Pointer of the field. It normalises hash values to lowercase hex, compiles every criterion, checks each rule’s order and priority against the precedence model, and flags rules that can match without a positive identity criterion (naming the criteria on one such path through the tree), rules that match on negations or context alone, allow rules whose only identity is weak, and unsupported regular expressions. A document that passes becomes a ValidatedPolicy.
  • decision: the typed Decision every consumer gets: outcome, the enforce-mode outcome (would_have_been), the deciding action and rule (RuleRef), audit annotations, the mode, directives, effects with defaults applied, a reason code and a trace ID. Its JSON form is stable and snapshot-tested. Decision::from_rule builds the enforce-mode decision of one deciding rule, and Decision::implicit_deny the decision when none decides. The pipeline adds the rules the deciding rule overrode, the audit annotations and the trust-source grants (#35), then applies the effective mode (#36): would_have_been keeps the enforce-mode outcome, and learning_candidate marks an object to learn.
  • evaluate: the evaluation pipeline (#35). An Evaluator compiles a validated policy once, and Evaluator::evaluate decides one object in fixed stages: the mandatory deny tier, exclusions (ignore), the policy’s precedence model, then the implicit deny. See Precedence. Evaluator::evaluate_in then applies the device’s modes; see Modes. evaluate::index files every rule in candidate indexes when the policy is compiled, so an evaluation only evaluates the rules that could match (#42); Evaluator::evaluate_with is the lazy fact protocol.
  • unknown: stage 6, the unknown-application policy (#39). See Unknown applications.
  • lifecycle: rule activity windows, exceptions, review campaigns, expiry notices, bulk change sets and per-rule hit counters (#40). See Rule lifecycle.
  • analysis: the policy assistant, analyse(policy, facts, now) -> Vec<Finding>, and the publish gate (#40). See Policy assistant.
  • mode: enforcement modes (#36). mode::resolve gives the effective mode of one decision from the policy, the object type, the deciding rule and the device state (DeviceState: base mode, connectivity, override session, lockdown); ProtectionStatus reports a device’s protection; mode::machine is the state machine of legal mode changes, with time boxes that revert on a monotonic and a wall clock.
  • library: reusable libraries (#37): rule sets, application definitions, match fragments, and hash, publisher, path, principal, device, network and schedule sets, and message templates. A ref node in a match tree names one by ID and pin (latest or a version). Catalogue checks every library version, resolves references and rejects reference cycles, naming the path. Catalogue::expand replaces each reference with its tree. Libraries are global (read-only to tenants) or one tenant’s, have an owner, and can be duplicated into an editable copy that records derived_from.
  • hierarchy: the scope hierarchy (#37): global, tenant, nested groups (at most 8 deep), devices, dynamic groups and templates, with the built-in unassigned, unmanaged and staging groups. HierarchyDocument::validate checks a snapshot, and ValidatedHierarchy::effective_policy computes one device’s effective policy: a pure function of the snapshot, the libraries at their resolved versions and the device’s dynamic groups, with per-rule and per-setting provenance and a content hash. place runs the automatic placement rules. See Hierarchy.
  • trace: the decision trace, explanations and the policy simulator (#41). See Trace, explain and simulate.
  • engine: what the agent decides through (#42). An Engine holds the current policy snapshot and swaps a new one in atomically (Engine::load): decisions in flight finish on the old one, and reading it takes no lock. Engine::evaluate checks the decision cache, then decides with the facts computed so far or answers NeedFacts, under a per-decision time budget. See Performance.
  • demand: the classes of facts (FactSet) that the lazy fact protocol asks for, and the fixed order of its rounds.
  • precedence: the five precedence models, each a pure function from the matching rules to one winner (Precedence::resolve), and the specificity tiers that specificity ranks by.
  • facts: the facts about one object that criteria test (ObjectFacts): hashes, version-resource strings, the normalised path with its ACL safety, and the signatures with their verification status. Path variables (%PROGRAMFILES% and so on) are supplied per evaluation. Facts are computed elsewhere (#3, #4); this crate only reads them.
  • context: the user, device, session, network and time of one evaluation (EvaluationContext), which context criteria test: SIDs, group and tag sets, account names, host and domain names, directory units, the OS version and build, the token’s integrity level, yes-or-no facts such as user.is_admin, the session type, ID and client address, local addresses, DNS suffixes and network locations, and the weekday, time and date in the policy’s clock. As with object facts, the agent collects them (#4); a fact that was not collected is unknown.
  • condition: compiles a rule’s match tree (CompiledMatch) into an arena of compiled criteria and evaluates it with Kleene three-valued logic. all stops at the first NoMatch and any at the first Match, and the order of children never changes the result. Only Match makes a rule match, and Unknown counts as no match for every action. An allow rule therefore cannot allow on an unknown fact (it fails closed), but a deny rule does not block on one either. That is the default (no_match) that #32 sets for deny rules; a deny’s unknown_as and on_unparseable options change it (see Unknown facts).
  • scope: rule scoping (#38): who, where and when a rule applies. See Scopes.
  • bundle: the canonical compiled policy bundle (#43). bundle::cbor is its encoding: a strict subset of CBOR in the core deterministic encoding of RFC 8949 §4.2 (shortest integers, definite lengths, map keys sorted by their encoded bytes and never repeated, no floating point, tags or simple values other than false, true and null, and NFC text). The encoder can only write canonical bytes, and the decoder accepts only canonical bytes, within limits on size, depth and item count, so it is safe on untrusted input. bundle::keys is the stable registry of integer keys that replace field and variant names in a bundle; an ID is never reused, tests/golden/bundle-keys.txt holds every published one, and a key’s sign says whether a reader that does not know it refuses the bundle (critical, 0 and up) or skips it (ignorable, below 0: only descriptions and display fields). bundle::serial writes any model type through serde as CBOR with those keys and NFC text, and reads it back with the model’s own strict readers. A test fails if a field or variant of the model has no key, and governance metadata (justifications, tickets, comments) has none, so it cannot reach a bundle. bundle::format is the bundle itself: [header, body]. The header (format and schema version, tenant, group or device target, policy_version, min_agent_version, generated_at, optional expires_at) decodes on its own with decode_header, which palisade-proto calls for the envelope checks (#225). The body holds the policy in canonical order (rule sets, rules, assignments and profiles sorted by ID or name), the inlined library sets its scopes read, the source revisions and a digest of the governance metadata kept on the server. PolicyBundle::decode refuses anything that is not exactly what to_bytes writes, apart from unknown ignorable fields, and PolicyBundle::validate then validates the body as a policy. bundle_hash is SHA-256 over the bytes; decision_hash covers only what decisions depend on (not the header, sources, metadata digest, revision, names or descriptions), for the decision cache (#42). bundle::compile builds a bundle from a validated or effective policy and its library catalogue: it inlines each library set a scope reads at its pinned version, records the sources, and fails with a retriable CompileError when a set is missing or the bundle is over the size limit. It first runs the policy assistant (#40) as of the header’s generated_at: an error finding stops it (CompileError::Blocked) unless Source::admin overrides it with a reason, and Compiled::gate returns the override and the findings it covers for the audit record. BundleSets resolves those inlined sets when a loaded bundle is evaluated, so the agent and the simulator decide alike. bundle::load(bytes, limits, baseline) is the agent’s one step from verified bytes to a LoadedPolicy: it decodes, validates, adds the agent’s own system_baseline if given, and builds the evaluation indexes and location profiles with the bundle’s inlined sets. Engine::from_loaded and Engine::install take the result, and any failure leaves the current policy in place. tests/budget.rs loads the reference policy (100,000 hash rules) as a bundle within the #42 load budget. bundle::delta gives diff and apply: puts and removals of rules and rule sets by ID, plus replacements of the policy, libraries and sources. apply works only on the exact base and checks the result against result_bundle_hash. worth_sending sends a delta only to that base, and only when it is under half the full size. Tests: unit and property tests for each layer, golden bundles with their hashes in tests/golden/bundles/ (tests/bundle_golden.rs, regenerated with PALISADE_BLESS=1), and the fuzz_bundle_decode fuzz target.
  • ops: compiles one criterion (CompiledCriterion) and evaluates it against facts, giving Match, NoMatch or Unknown with notes for the decision trace. The module docs define the semantics: several values, negation of unknown facts, case folding and Unicode NFC, path normalisation and wildcards, alternate data streams, path variables, the path-ACL rule for allow rules, version comparison, and which signer statuses can match. Regular expressions use a linear-time engine; look-around and backreferences are rejected with a guided error. The numeric, integrity-level, date, network (ip_in_cidr, ip_between, ip_wildcard), set (member_of, any_of, all_of) and time (weekday_in, time_between, date_between) operators and the criterion options anchored, match_ads, include_sub_ous and safety_critical are described there too. ops::net parses the addresses, CIDR blocks, ranges and MAC addresses that criteria test.

Each identity field has a strength (Field::strength, #31): strong for SHA-256-family and Authenticode SHA-256 hashes, the leaf thumbprint and the TBS hash, medium for the publisher and full or directory paths, and weak for everything else, including the SHA-1 thumbprints and what names a certificate authority (the issuer, the PCA, the root thumbprint and the EKUs). A TBS hash at a position other than leaf can name a CA, so validation counts it as weak in an allow rule. For precedence, the leaf thumbprints and the leaf TBS hash (position: leaf) rank with the publisher (tier 4); the issuer, the PCA, the root thumbprints, the EKUs and a TBS hash at any other position name a certificate authority (tier 7). Path normalisation (palisade_core::path) is shared with the agent, so facts and rule values are normalised the same way.

Signer criteria (#31, ops::signer) match if any signature satisfies them. A criterion’s signer options choose which signatures take part (accept_status, allow_digest_mismatch, source, signature_index) and what the same signature must also satisfy (signed_after, countersigned, min_key_bits, disallowed_algorithms); component picks the publisher’s CN, O or full DN, and position the TBS hash’s place in the chain. A fact a test needs that was not determined makes that signature unknown, never a match. Only allow_digest_mismatch lets a tampered file match, and validation warns about it, and about an allow that accepts other untrusted statuses (signature_status_relaxed). model::preset::PublisherProduct builds the recommended allow form, publisher_product: a publisher and a product name, optionally with the original file name and a version range (ISM-1471).

§Precedence

A file often matches several rules. Evaluator::evaluate decides it in fixed stages, whatever the model (#35, ADR 0004):

  1. Mandatory deny. A matching rule of a mandatory blocklist blocks (mandatory_deny). No allow, elevation, trust source or exclusion changes that, under any model.
  2. Exclusion. A matching ignore rule makes the object ignored.
  3. Policy. The policy’s precedence_model chooses among the matching allow, allow_contained, allow_elevated and deny rules.
  4. Unknown. If nothing decided, the policy’s unknown policy decides; its default is the implicit deny (implicit_deny_unknown, #39). See Unknown applications.

Between stages 1 and 2, one of Palisade’s own pinned images (Evaluator::with_self_images) is allowed (self_allow).

An override session (#9) lowers the mode of stages 3 and 4 (see Modes); post-allow attribute rules (#33) are the stage still to come between them. The result is the enforce-mode decision; Evaluator::evaluate_in applies the modes on top of it. audit rules never decide: every one that matches is an annotation. trust_source rules never let an object run: their grants are attached only to an allowed object. defer rules have no opinion. When several mandatory denies or exclusions match, the most specific decides.

The decision names the deciding rule (matched_rule) and every rule it overrode (overridden): the other candidates of the deciding stage, every candidate of the later stages, and the trust sources of an object that is not allowed.

ModelDecidesOptions

Options live in policy.precedence_options; one the model does not use is a warning (precedence_option_unused).

  • allow_tiebreak: when several allows could decide, most_restrictive (the default) prefers allow_contained, then allow, then allow_elevated; most_permissive reverses that.
  • granularity_tiebreak (allow_wins): within one rule set, only the most specific matching rules take part, so a denied file in an allowed folder stays denied.
  • same_tier_tiebreak (specificity): deny (the default) or allow.
  • curated_first (first_match, on by default): rules of read-only rule sets come before every custom rule.
  • priority_direction (priority): lower_wins (the default) or higher_wins.

Specificity tiers, from a rule’s strongest identity that every match must satisfy (all takes its strongest child, any its weakest, not and context criteria identify nothing): 1 hash, 2 signer with file name and version, 3 signer with product name, 4 signer (the publisher, a leaf thumbprint or the leaf TBS hash), 5 full path (path.full equals), 6 directory (deeper first), 7 metadata, a certificate authority (the issuer, the PCA, a root thumbprint, the EKUs or a TBS hash at a position other than leaf), or nothing.

Order and priority. Under first_match, every rule that allows or denies needs an order (order_required). Rules of custom rule sets use 100001 to 999989 (order_reserved). 0 to 99 is for system rules, 100 to 100000 for curated rule sets, and 999990 to 1000000 for defaults and catch-alls. Under priority, every such rule needs a priority (priority_required). Two rules with different actions at one priority are a warning (duplicate_priority). A newer rule is one with a higher rule ID, because rule IDs are UUIDv7s, which start with their creation time.

Catch-all rules (#33, #329). catch_all: true marks a rule set’s default: the only rule that may have no identity anchor, and the only one whose match may be an empty all, which matches every object. It is a floor at stage 4, below the managed system_baseline: it decides only when no other allow or deny matched, under every model, whatever its order or priority. A catch-all is named Default… or contains Catch-all, allows or denies, is never in a mandatory rule set, and a rule set has at most one (invalid_catch_all). One that lets objects run needs the policy’s confirm_permit_all: "I UNDERSTAND" (permit_all_unconfirmed) and is rejected under a compliance preset (unknown_allow_not_permitted). Under first_match it may use the catch-all order range, and a policy without an enabled one gets the warning catch_all_missing; objects nothing matched then fall to the unknown policy, which blocks by default.

Determinism. Every choice ends with the unique rule ID, and the lists in a decision are sorted by rule ID. So a decision never depends on the order of rule sets or rules in a document, under any model. Only first_match and priority depend on order and priority, by design.

§Unknown facts

A rule applies only when its tree is Match, so an unknown fact never allows, trusts or excludes. A deny chooses how it treats what it cannot decide:

  • unknown_as: match makes the deny apply when its tree is Unknown, so it blocks unless the model prefers an allow. The default, no_match, means an unknown fact does not block.
  • on_unparseable: match makes each criterion whose version fact is not a version count towards the deny applying (as Match, or NoMatch under an odd number of not nodes). The rest of the tree must still match. The default leaves the criterion Unknown.

Mandatory denies use the same options and defaults. Making the shipped blocklists fail closed by default (safety_critical) belongs to #32 and #87.

§Modes

policy.mode sets how a policy’s decisions take effect (#36):

ModeDecision
disabledOnly a device can be disabled (see the state machine below). The engine is not consulted: evaluate_in returns None, and not even a mandatory deny applies.
monitorEvaluated fully. A would-block runs as allowed_audit, with would_have_been: blocked.
auditAs monitor; the agent sends a full event for every decision rather than would-blocks and summaries (#16).
learningAs audit. An object that no rule decided, so that stage 6 handled it, is a learning_candidate (#5). An object a deny rule would block is never one.
enforceBlocked means blocked.

A relaxed block keeps the deciding rule and its effects, so the would-block event is still logged, but notifies nobody and carries no kill_running or request. A mandatory deny blocks in every mode and every override session (#125: the blocklist always wins); only a disabled device skips it. A relaxed deny never lets through what an enforcing rule blocks: the matching rules are decided again without the denies that do not enforce, and if an enforcing deny or the implicit deny then blocks, the object is blocked. If an allow decides instead, the object runs with that allow’s containment, elevation and grants. An override session is applied as a second layer, after the modes: only what the modes still block can become allowed_override, and the decision names the enforcing rule the session bypassed.

Where modes are set, resolved for each decision by mode::resolve:

  1. Lockdown (DeviceState::lockdown, from the bundle) forces enforce over everything below, including a disabled device. Clearing it restores every prior mode.
  2. Device mode: the policy’s mode, or the mode the state machine moved the device to. disabled stops here.
  3. Mandatory deny: always enforce.
  4. Disconnected: policy.mode_options.mode_disconnected, if stricter, while the device has not checked in for disconnected_after_secs (default 3 check-in intervals). It must be at least as strict as mode (mode_disconnected_weaker).
  5. Object type: mode_options.mode_by_type (for example script.powershell: audit). The control levels in settings then cap it: audit at audit, off at monitor.
  6. Rule set: a non-mandatory blocklist’s mode_override replaces it (mode_override_not_allowed elsewhere).
  7. Rule: on a deny, enforcement_override: always_enforce makes it enforce; never_enforce caps it at audit. Other actions cannot set it (enforcement_override_not_deny).
  8. Override session (#9): caps it at audit (allowed_override), except for an always_enforce rule unless the session is full_bypass.

disabled is rejected for a policy, an object type and a rule set (mode_not_allowed). Strictness ranks enforce above learning and audit, above monitor, above disabled.

Protection status (ProtectionStatus::of): lockdown, disabled, override_active, then protected_enforce if every Essential Eight object type is enforced, protected_partial if the device mode is enforce but some type is not, and otherwise audit, learning or monitor.

State machine (mode::machine::ModeMachine). Legal changes: disabled to any mode; monitor to audit, learning, enforce or disabled; audit to learning, enforce, monitor or disabled; learning to audit, enforce or disabled; enforce to any other mode, time-boxed. Leaving enforce for a weaker mode, and entering disabled, needs a reason, a ticket where the tenant requires one, and an expiry at most 30 days ahead; only enforce to audit may be permanent, with the elevated permission. A time box ends when the wall clock reaches the expiry or the monotonic clock has run for its length, so setting the clock back cannot extend it; the device then returns to the mode it left, offline too. Observing the end is final: current and tick both close the box and store the rollback target, so a later read with the clock set back never brings the weaker mode back, and the read that observes it returns the expiry record. Each change gives a ModeChanged record for the mode_changed event (#16). Time comes from the caller (Clock, Now).

Readiness gate. When the readiness check (trace::readiness, below) says ack_required, the caller sets Governance::readiness_ack_required, and a requested move to enforce is rejected (ReadinessAckRequired) unless it carries readiness_ack; the record then has readiness_acked. Returning to enforce from a time box that left it, and the revert when a box ends, are never held back.

Event fidelity (mode::events::fidelity). Which decisions a mode reports; the agent emits them (#16). A disabled device reports nothing. ignore is never reported. A block keeps its rule’s log. A would-block and an override-session allow are always an event. An allowed object follows its rule’s log in enforce, is only summarised in monitor (nothing for log: never), and is a full event in audit and learning. A learning candidate’s event carries the object’s full facts (#5).

§Hierarchy

A device’s effective policy is built from layers, outermost first: the global node, its tenant, its groups from the tenant down, its dynamic groups (highest rank first), and the device. A node linked to a template has the template’s layer just before its own. On one node, policies apply by slot_order, and the lowest slot wins a conflict. The module docs of hierarchy have the full semantics. In short:

  • Rules are additive. The effective rule list is the union of every layer’s rule sets: those of assigned policies, of assigned rule set libraries (rule_sets, with a pin) and of every rule set library in an assigned category, including ones added later. Each rule keeps its provenance (EffectivePolicy::rule). A rule set two layers contribute is included once. Two different rule sets with one ID, or two versions of one library, are rejected.
  • Removal. A child cannot delete an inherited rule. It can suppress one (suppress_inherited) when the rule set allows it: allow_child_suppress defaults to true for allowlists and baselines and to false for every other kind. A mandatory rule set can never be suppressed (suppress_not_allowed), so the #125 rule that the blocklist always wins holds below every node. A suppressed rule stays in the effective policy, disabled, and its provenance names the node. A child can also shadow a rule with one that wins under the precedence model. Nothing shadows a mandatory deny, because it is decided before every model.
  • Settings are override-by-nearest, per top-level key of settings and per mode option. A node’s own settings beat its policies. A key in locked_settings keeps its value for every layer below, and a later attempt is reported as blocked_by_lock. locked_settings can also lock mode_options.mode_disconnected, mode_options.disconnected_after_secs and mode_options.mode_by_type.
  • Modes. Each layer’s mode is the node’s mode, or its policies’ modes merged by mode_merge: closest (the default) or strictest. The built-in unassigned group audits unless it sets a mode, and so does a device with no mode anywhere. lock_mode: true sets a floor at the mode in force at that node. A weaker effective mode, type mode or rule set mode_override is raised to the floor, and so is a control level that would cap below it. With an enforce floor, never_enforce rules become inherit. Every change is listed in ModeProvenance::adjustments.
  • Precedence. The model is chosen by the global node or the tenant, or by a group if its tenant allows it (precedence_not_allowed). With no node choosing, the highest-ranked policy’s model applies. Every policy in one effective policy must use that model (precedence_conflict).
  • First match across levels. Each rule set carries the band of the first layer that contributed it (RuleSet::band). The hierarchy sets the band and replaces any value a policy gives. level_order: top_down (the default) puts global rules first, then the tenant, the groups from the tenant down, the dynamic groups and the device. bottom_up reverses that order, and flat ignores levels.
  • Determinism. The content hash is the SHA-256 of the effective policy’s canonical JSON (sorted keys, revision left out) with the resolved library versions. It never depends on the order of anything in the snapshot (property-tested).
  • Unknown-application limits. A device’s effective policy holds at most limits::MAX_UNKNOWN_SCOPE_VALUES (20,000) unknown-application scope values: over every contributing policy, its scope and its unknown.scopes. Building one at that size takes about 40 ms and serialises to about 1.5 MiB (release build; about 77 bytes per value), and each agent receives it. Snapshot validation rejects a hierarchy where any device could exceed the cap (too_many at the node’s assignments), so an effective policy from a valid snapshot never does. The check is an upper bound: a node’s own layers plus every dynamic group of its tenant, because a device’s dynamic groups are only known when its policy is computed. It is pessimistic for tenants with many dynamic-group policies, and the error lists the largest contributors, dynamic groups included.
  • Placement. Each tenant’s placement rules are first-match on directory OU, directory group, hostname wildcard, CIDR, tags and OS, and end with an implicit catch-all to unassigned that cannot be removed. A group can opt out of placement as a source and as a target (allow_auto_assignment: false). Placement runs on first contact and on reconnect, and on a user change only if the tenant sets place_on_user_change.

§Performance

Evaluation is not linear in the number of rules (#42). When a policy is compiled, each rule is filed under its anchor: keys that the facts must hold for the rule to match. They come from a positive hash, leaf thumbprint, leaf TBS hash (signer.tbs_hash with position: leaf; a CA-position TBS hash is shared by everything that CA signed, so it is evaluated for every object), publisher, issuer, version-resource string, file name, extension, path prefix or principal criterion, outside any not. all takes the anchored child on the cheapest facts (the path and the context before hashes, signers and the version resource), then the most selective, so a rule’s expensive facts are only asked for once its cheap ones match; any takes the union of its children, if each has one. Hash sets are sorted arrays of raw digests, searched by bisection, so a million-entry set costs one lookup and 36 bytes an entry. A rule that is a single hash test is matched from the validated document’s values, without a second compiled copy. Paths are filed by their literal prefix, cut at a separator: a wildcard C:\Program Files\*\x.exe under C:\PROGRAM FILES. A rule with no anchor, and a deny with unknown_as: match, is evaluated for every object of its types; validation warns when a policy has more than 500 of them (unindexed_rules). Mandatory denies have their own indexes, and are evaluated before every other rule. A fact that rules are indexed on but that is missing, malformed or unresolved makes the decision rest on an unknown fact, so it is never cached. A property test checks that the indexed evaluator gives exactly the decision of a linear scan, and the same deciding rule, for random policies, facts and device states.

Lazy facts. Evaluator::evaluate_with takes the classes of facts computed so far (demand::FactSet): the path, process and user are always known. If a rule that could still match reads a class that is missing, it answers NeedFacts with the classes of the next round, in a fixed order: hashes, then signatures and the version resource, then the path ACL. It only asks for a class that a rule not yet ruled out by the facts computed so far reads, so a decision takes at most three rounds, and none if no rule could match. Evaluator::required_facts says what a policy reads at all, so the agent can hash eagerly when hash rules exist.

Decision cache (engine::cache). Keyed, with a random SipHash key, by the file’s identity (volume, file ID, change stamp and size, or its SHA-256), the object type, a hash of only the principals and context facts the policy tests, the object’s path facts, the device state and the policy snapshot. A bounded, sharded LRU (32 MiB by default, counting each whole decision). Entries go on a policy swap, on a file change notification (Engine::invalidate_file), on logoff (Engine::invalidate_session), at a deadline such as the next schedule boundary, and after decision_cache_ttl_secs. A decision is never cached if it rests on an unknown fact, prompts the user (an approval request, a reason prompt, re-authentication or a custom notification), is made in an override session or in learning, or while the clock is not trusted. A property test checks that a hit is always the decision a fresh evaluation gives.

Watchdog. The budget (50 ms by default) is checked after each match tree; once it is spent, no further tree is evaluated. A mandatory deny that already matched then decides, as always (ADR 0004), and if the mandatory tier was not finished the object is blocked. Otherwise the decision falls back to on_eval_timeout: block when the object’s type is enforced, allow_audit otherwise, either one configurable. The result names the slow rule for the policy.eval_timeout health event. PerfProfile (workstation, server, multi_session) only tunes the cache and eager hashing; decisions never change.

No allocation per decision. Evaluation folds text into thread-local buffers and keeps the lists of a decision inline, so a warm decision allocates nothing on the cached and uncached paths. tests/allocations.rs checks this with a counting allocator. The decision trace’s standard and full levels (#41) allocate by design; a rule’s notification text, help URL, tags or trust-grant paths are copied into a fresh decision.

§Scopes

A scope narrows a rule to some users and groups, devices, network locations, sessions and times (#38). It can be set on a rule, on a rule set’s assignment (policy.rule_set_scopes, which covers every rule of the set) and on the policy (policy.scope). Scopes intersect down that chain: a rule applies only when its match tree matches and every scope on the way to it matches. A rule out of scope behaves as if it were absent. It never decides, it is not listed as overridden, and a scheduled deny outside its windows does not deny. Scopes are evaluated before the match tree. They never count towards a rule’s identity anchor or its specificity, so the precedence model chooses among the rules in scope exactly as before. See docs/examples/policies/scoped-rules.yaml.

Rules of evaluation. An empty scope matches everything, and an empty include means everyone or everything. A match in exclude always beats include. A scope evaluates to match, no match or unknown, with the three-valued logic of match trees, and unknown follows the rule’s action: an allow, trust source or exclusion never applies on it (it fails closed), and a deny applies only with unknown_as: match. Group membership is tested against the subject’s token: its group SIDs, which already hold nested directory groups and local groups, kept sorted so that a test is a binary search. Cloud-directory groups are not in the token. The agent caches them on the device with cached_at, and a cached membership older than settings.group_cache_max_age_secs (default 86400, range 3600 to 86400), from the future, or read with an untrusted clock is unknown (scope_stale). A deny-only SID in a filtered administrator token (UAC) is read both as membership and as none, and a rule takes the reading that makes it apply less if it lets an object run, and more if it denies or audits (deny_only_group). So a non-elevated administrator never gets an administrators-only allow, and is never let off a deny that excludes administrators. Absence from a token is proven only when its user SID and groups were both collected and are well formed, because the user SID is not among the groups. A SID set or cloud-group cache with a malformed entry cannot prove absence either (fact_malformed).

Membership in token groups changes only when a new token is created, at the next logon. Removing a user from a group may therefore need them to log off before scopes see it. Cached cloud groups refresh on the configured interval, or on a manual refresh command (#4).

Name patterns (user_pattern) match the account name, which is easier to spoof than a SID. Validation only accepts one where a match makes the rules it covers apply less if they let an object run, or more if they deny (user_pattern_not_allowed). That rules them out of allow includes. Audit rules may use them anywhere.

Schedules. timezone_basis is device_local, utc or user_local, defaulting to settings.time_zone_basis. user_local uses the session user’s time zone if the agent could read it, and otherwise the device’s (timezone_fallback). Zones are IANA names, read from the time zone database bundled into the binary. windows are {days, start, end | duration_mins}. A window starts on one of its days at start, includes its start and excludes its end, and may wrap midnight (22:00 to 06:00). dates limit the schedule to absolute date ranges and except_dates remove days such as holidays. Both test the local date of the instant decided. Across daylight-saving changes, a local time that occurs twice means its first occurrence, and a skipped one moves forward by the gap. This is the “compatible” rule of the ECMAScript Temporal proposal. A scheduled rule outside its windows is absent. If the agent’s trusted time is missing or its integrity is flagged (#18), or the zone is unknown, scheduled allows go inactive and scheduled denies stay active (clock_untrusted). On an allow, in a scope with combine: all and no negate, so that the rule stops applying when the schedule closes, on_window_close (none, warn, warn_then_terminate, with grace_secs, default 300) gives the decision a window_close directive with the instant the schedule closes, for the agent and tray to act on (#4, #11). A schedule that is not well formed, such as an unvalidated library schedule, reads as an untrusted clock does (fact_malformed).

Network location. policy.location_profiles names locations such as corporate (dns_suffix: corp.example.org and server_reachable: true). The agent evaluates them with scope::CompiledProfiles on every network change and heartbeat (60 seconds by default). scope::LocationTracker keeps the previous location until a new one has been stable for 5 seconds, and scopes test the result with location_profile.

Library sets. principal_set, device_set, network_set, schedule_set and client device_sets refer to library sets by {id, pin}, where pin is latest (the default) or a version number. Hierarchy validation checks each one like a tree reference, pins it to the version it resolves to, and counts it for in-use checks, so a new version of a set changes an effective policy’s content hash. A schedule set holds one schedule, written as JSON. Evaluator::with_library, trace::Tracer::with_library and Simulator::with_library resolve principal, network and schedule sets through a scope::ScopeLibrary (#37 provides one: ResolvedLibraries). A set it cannot resolve is unknown (set_unresolved). Device-set membership is worked out by the server and arrives as a fact.

Every stage-6 decision is unhandled and carries unknown: the resolved and applied levels, the entries that applied, any fallback reason, and the object’s locations and origins. Location classes come from the agent (ObjectFacts::location_class); without them the engine classifies the path (unknown::classify), and a class whose deciding fact is missing (no usable path, no ACL fact, no volume kind, an unset variable) is Unknown, never a definite match: see below. Both spellings of a path with an alias are classified.

Missing facts never make an object look safer (ADR 0018). A location class can relax a decision as well as tighten it, because stage 6 takes the most restrictive entry among an object’s classes and default when none has one. So the classifier never grants a class from a guess. Each location class and origin is three-valued, with the crate’s Kleene logic: Match (the facts establish it), NoMatch (they rule it out) or Unknown (a missing fact could make it true). Stage 6 resolves and applies the level of the Match classes as above, then applies each Unknown class’s entry (or default where it has none) too, and the most restrictive applied level wins (fallback missing_fact). Removing a fact can only make a class Unknown, so it never lowers the level; with every fact present nothing is Unknown and every class and decision is what it was before. The decision’s unknown carries unknown_locations, unknown_origins and missing_facts, and the explanation names the missing facts.

  • Path variables. With a variable set, it decides the classes it covers (Match or NoMatch): a %PROGRAMFILES% listing only C:\Program Files makes C:\Program Files (x86) not program_files. Without it, those classes are Unknown for every path: windows and %WINDIR%\Temp without %WINDIR%, program_files without %PROGRAMFILES%, temp without %TEMP%, user_profile without %USERPROFILE%, %APPDATA%, %LOCALAPPDATA% or %PUBLIC%. There are no drive-root guesses: X:\Windows, X:\Program Files and X:\Windows\Temp are not the system’s folders unless the variable says so.
  • Volume kind (PathFact::volume). Without it, removable, optical, network (for a drive path) and the classes that need a fixed volume (program_files, windows, other_fixed) are Unknown.
  • Path. With no usable path, every class the path decides is Unknown, except that a known removable, optical or network volume still rules out program_files, windows and other_fixed.
  • ACL (PathFact::user_writable). Without it, user_writable_other is Unknown (unless a directory the scanner flagged establishes it). A writable ACL or a flagged directory is Match, and a safe ACL is NoMatch. So a policy whose user_writable_other entry is weaker than its default cannot be relaxed by dropping the fact.
  • other_fixed is a drive path on a fixed volume that is in none of user_profile, temp, program_files and windows, so it is Unknown whenever one of those is.
  • Origins (ObjectFacts::origin). None means origin collection did not run or report: every origin, unknown included, is Unknown, so the level comes from the type and location entries and default, and every by_origin entry joins as a possible candidate. Objects without origin facts can therefore be decided by by_origin entries. Under the default preexisting_policy: baseline_only, the preexisting origin then blocks: an agent that sends no origin facts gets every unknown object blocked in enforce mode (would-block in audit, monitor and learning), and missing_facts names origin. A reported set is complete; an empty one means no evidence was found, which is exactly {unknown}.

A missing fact can therefore make many objects stricter for a policy with a strict entry for the class it decides. That fails closed and only affects objects no rule decided; the endpoint agent is expected to supply every variable, the volume kind and the origin set.

Prompts. prompt.options is a subset of allow_once, allow_always_local, request_approval and block (default: all but allow_always_local), with require_justification, reauth (none, password, mfa), timeout_secs (10 to 600, default 60) and fallback (default block). A prompt is never shown for an object a blocklist rule matched (even one set aside by a non-enforcing mode), for a library or driver, or without an interactive session (a console or remote-desktop session of a user who is not the system account): those get the fallback. unknown::answer turns the user’s answer into the final outcome; a timeout or a prompt that could not be shown applies the fallback. allow_always_local creates a LocalApproval for the exact SHA-256, scoped to the user or device (local_approval_scope) and uploaded for review. For objects from the internet, email, removable media, a network share, or of unknown origin, or on removable, optical or network volumes, it expires after temp_approval_days (default 14).

Scope. policy.scope limits the unknown settings as it limits the rules (#38). For a subject outside it, or when a fact the scope needs is unknown, the settings do not apply and the built-in default decides: the implicit deny (implicit_deny_unknown, fallback policy_out_of_scope, and a trace paragraph that names the policy scope). So default: allow never reaches a device, user or session the policy does not cover. Validation checks policy.scope as an allow’s scope when any unknown level is weaker than block, so user_pattern cannot widen it. unknown.scopes narrows the settings further: they apply where policy.scope matches and any entry of unknown.scopes matches. An effective policy (#37) has no scope of its own. It carries each contributing policy’s limit, unexpanded, in the effective-only field unknown.scope_limits: one entry per contributing policy, {all_of: [policy.scope], any_of: unknown.scopes}. Its unknown settings apply to a subject when any entry holds (every scope of all_of and, if any, one of any_of), and to everyone if one contributing policy has no limit. Validation rejects scope_limits in an authored document. So the settings apply exactly where each contributing policy’s own evaluation would apply them, never more widely.

Inheritance. An effective policy’s unknown is the strictest combination of every assigned policy’s (UnknownPolicy::stricter). Levels are compared as stage 6 applies them, each with its own policy’s prompt fallback and containment profile: in every context (type, classes, origins, session, containment), the merged policy applies a level at least as strict as each policy’s. One policy cannot always reproduce two exactly, so where it cannot it is stricter, in three cases: the merged prompt fallback is the strictest of the policies that prompt; a restrict in one policy, next to a prompt with a blocking fallback in another, becomes block everywhere in the merged policy, including where the prompt could have been shown (a static merge cannot see the session: with A {default: allow} and B {default: restrict, by_origin: {internet: prompt}, prompt.fallback: block}, an internet script in a console session is blocked, though A allows it and B would ask); and entries merge key by key, so an entry only one policy sets is compared with the other’s default even where another of its entries decides the object. For example, with A {default: block, by_type: {executable: detect}} and B {default: detect, by_location: {temp: detect}}, each detects an executable in temp, but the merged policy blocks it. Each case fails closed. The scopes merge too: each policy’s scope and unknown.scopes become one unknown.scope_limits entry, so the merged settings apply exactly where some contributing policy would apply its own, and the implicit deny decides elsewhere. The hierarchy collects those entries in one pass, so building an effective policy is linear in its contributing policies.

Modes. A blocked or pending_user stage-6 result is relaxed to allowed_audit in a mode that does not enforce, so no prompt is shown in audit, monitor or learning.

Built-in safe defaults.

  • system_baseline (unknown::system_baseline, ValidatedPolicy::with_system_baseline, applied after validation by the agent or server with the OS facts it trusts): a managed, read-only baseline rule set with one allow for binaries with a trusted signature from the OS publishers the agent reports, under %WINDIR% or %PROGRAMFILES%, where no non-administrator can write. The known user-writable folders inside the Windows directory are excluded (unknown::baseline::MANDATORY_EXCEPTIONS: System32\spool\drivers\color, System32\Tasks, Windows\Tasks, Windows\Temp, the RSA MachineKeys store, System32\Com\dmp, System32\FxsTmp, System32\spool\PRINTERS and SERVERS, Registration\CRMLog, Windows\tracing), along with every directory the writable-path scanner flagged and any alternate data stream. It is a floor at stage 4: it is decided over only when no tenant allow or deny matched, so under every model (including first_match with curated_first) a tenant’s rule wins over it. A mandatory deny still blocks what it covers. Its inputs are checked: publishers are trimmed text, and flagged directories are drive or UNC paths with no stream or wildcard. The caller must supply the path variables %WINDIR%, %PROGRAMFILES% and %SYSTEM32% (the native and, on 64-bit Windows, the 32-bit system directory). Without %SYSTEM32% the System32 exceptions are unknown, so the allow cannot show a file is outside them and does not apply: OS binaries are then decided by stage 6, which blocks them under the default.
  • Self-allow. Evaluator::with_self_images pins the agent’s images (SelfImage::new: the facts the agent’s parser computed, the context the image runs in, and its publisher) by SHA-256 and trusted signer; a pinned image is allowed right after the mandatory tier. PolicyDocument::validate_with_self_images rejects every deny, mandatory or not, whose tree is not NoMatch on an image’s facts and context with the devices’ path variables (deny_matches_self): a deny that matches, or could match depending on facts it does not settle, could block the agent.

Compliance presets (UnknownPolicy::preset): e8_ml1 blocks in user_profile, temp and user_writable_other and detects elsewhere (ISM-1870); e8_ml2 blocks everywhere (ISM-1871); e8_ml3 also blocks drivers and requires a mandatory blocklist (mandatory_blocklist_required, ISM-1658). e8_ml3 keeps driver_boot_policy: audit: a driver loaded during early boot is reported, not blocked, because blocking an unrecognised boot-start driver can leave a device unable to boot (ADR 0018). The exemption is explicit: an e8_ml3 policy with driver_boot_policy: audit warns (compliance_weakened at /policy/unknown/driver_boot_policy) until it is set to enforce. A preset-tagged policy that is weaker than its preset for any type, set of one or two location classes and origin (with a prompt counted at its fallback) warns (compliance_weakened), and a silent allow in a user profile or temporary folder is an error (unknown_allow_not_permitted). Other checks: unknown_level_not_valid_for_type, restrict_profile_required, invalid_prompt_settings and unknown_allow (a warning).

§Rule lifecycle

Every rule, rule set and policy has metadata (#40): owner, justification, ticket_ref, requested_by, approved_by, approved_at, created_by, created_at, updated_by, updated_at, source (manual, learned, recommendation, catalogue, import, api, approval_request), review_by (a date), last_reviewed_at, last_reviewed_by, risk_rating (low, medium, high), compensating_controls, exception, tags and comment. Instants are RFC 3339 date-times, read as UTC; dates are RFC 3339 full dates. Metadata never changes a decision: PolicyDocument::decision_relevant strips it (and the governance settings), the form a bundle’s decision-relevant hash is taken over (#43).

Activity. A rule may have activates_at and expires_at. Outside that window, or with enabled: false, it behaves as absent: it never decides, annotates or grants. lifecycle::activity says why (disabled, not_yet_active, expired), and lifecycle::inactive_matches lists the inactive rules that would have matched, for the decision trace (#41). Evaluator::at (or set_clock) sets the clock, a RuleClock of the agent’s time now, its floor (the lower bound on real time the agent keeps in protected storage, ADR 0012) and whether it is anchored (ADR 0018). While the agent is offline-started (RuleClock::offline_started: after a restart, before its next check-in, with only the wall clock), a time-bounded rule that lets an object run, trusts it or excludes it is inactive, as with no clock: grants from the bundle do not start or continue (ADR 0018 rule 2). Anchored, each rule fails closed. A rule that lets an object run, trusts it or excludes it is active only while both readings are inside its window, so an expired allow never revives after the clock is set back, and setting the clock forwards cannot start one early. A deny, audit or defer is active while either reading is inside, so setting the clock forwards cannot end it early. With no clock, a time-bounded permissive rule is inactive and any other is active.

on_expire: deactivate (the default), delete_after_days: N (absent at once; lifecycle::retire_due lists it for deletion N days later), or convert_to_audit (it only annotates once expired).

Exceptions. lifecycle::is_exception: an ignore, an allow whose identity is weak or a path, or metadata.exception: true. Governance mode (policy.governance.require_justification, default on for a policy with a compliance preset) rejects an allow, trust, exclusion or exception rule without a justification (justification_required), an allow or trust rule with neither review_by nor created_at (review_date_required; review_by defaults to a year after created_at), and an exception without approved_at, expires_at at most 365 days after it, approved_by and risk_rating (exception_incomplete). The year counts from approved_at only: created_at and last_reviewed_at never stretch it, an attest review leaves it, and only a renew review moves it (to the review, for at most 365 days). Governance mode applies to every rule set the policy references, read_only (curated) ones included: read_only only affects precedence (curated_first, the reserved order ranges). The one exemption is the managed system_baseline, which is never part of an authored document: the engine adds it after validation (ValidatedPolicy::with_system_baseline), and a document containing a rule set with its ID is rejected (reserved_rule_set_id). Across a hierarchy, each layer’s governance mode is resolved against its own preset before merging, so a nearer layer cannot switch off a mode an outer layer gets from its preset. Also checked: invalid_activity_window, on_expire_not_applicable and invalid_governance.

Reviews and notices. lifecycle::review_due(policy, as_of) lists the rules due for review, sorted, and review_summary gives deterministic evidence-pack counts (ISM-1582). lifecycle::review applies attest, renew or retire, updating last_reviewed_* and review_by. lifecycle::expiry_notices(policy, since, until) gives the rule.expiring notices due in a window, at governance.expiry_notice_days (default 14, 3 and 0 days before) for the owner (#16). lifecycle::bulk applies enable, disable, extend or retire to several rules as one ChangeSet with a reason, or changes nothing: an exception is extended at most 365 days past approved_at, and a rule is enabled only if governance mode would accept it.

Hit counters. Evaluator::counters() gives a Counters with one lock-free slot per rule, by ordinal. record(decision, object, at) counts the deciding rule and each annotation; hit_key(ordinal, key, at) is the hot-path form (about 2 ns, benchmarked in criterion_eval). Each slot keeps hits_total, hits_since_report, last_matched_at and a 1 KiB HyperLogLog sketch of distinct objects (about 3% error). report(at) takes a HitReport for the policy revision every governance.counter_report_hours (default 24, 1 to 168) and on a policy change, and restore carries the last report across an agent restart, once per Counters: a snapshot (marked snapshot: true) keeps its unreported hits pending, while a sent report restores with nothing pending, so no hit is reported twice. The server merges sketches across devices for distinct_devices (#10).

§Schema versioning

Documents carry schema_version (semver). A reader accepts the same major version and any minor version. A minor version adds optional fields; a major version is a breaking change and gets a new schema file. PolicyDocument::from_json checks the version before reading the rest of the document.

The test committed_schema_is_current fails when the committed schema is stale. After changing the model, regenerate the schema:

PALISADE_BLESS=1 cargo test -p palisade-policy --test schema

§Editor support

Policy files can name the schema in their first line, as the examples and dsl::to_string do:

# yaml-language-server: $schema=https://raw.githubusercontent.com/jusso-dev/palisade/main/schemas/policy/v1.json

An editor that uses the YAML language server then completes field names and enum values and shows each field’s description. To check it by hand: open docs/examples/policies/minimal.yaml in such an editor, start a new line under policy: and request completions (the list includes precedence_model and settings), then change mode: audit to mode: strict (it is underlined as not one of the allowed values). To use a local copy of the schema instead, change the URL to a relative path, for example $schema=../../../schemas/policy/v1.json.

Unit tests cover each mode’s effect on a decision. palisade-core, palisade-fileid. Must never depend on an async runtime, an HTTP client or Windows API bindings. The rules are enforced by cargo xtask check-deps.

§Platform support

All platforms. This crate uses std. Only palisade-core has to build without it.

§Dependencies

  • regex-automata and regex-syntax: the engine and parser behind the regex crate, for linear-time regular expressions with RE2 semantics, also used to compile wildcards (#32). Patterns are parsed once and built from the parse tree with only the linear-time engines enabled. regex-syntax also recognises look-around and backreferences, so the error can explain the alternative. Both are already in the lock file through boon.
  • unicode-normalization: NFC normalisation before strings are compared (#32).
  • sha2 and hmac: the SHA-256 content hash of an effective policy (#37), deterministic trace IDs from event IDs in the simulator, and keyed digests of facts a trace withholds (#41). Both are from the same family as the hashes in palisade-fileid, and are already in the lock file.
  • jiff: civil dates and times, IANA time zones and daylight-saving arithmetic for schedules (#38), with the time zone database bundled into the binary (tzdb-bundle-always, no other default features), so evaluation never reads the system. It replaced chrono and chrono-tz, which cargo deny reports unmaintained.
  • arc-swap: the atomic, lock-free swap of the policy snapshot (#42). Readers never wait for a swap.
  • self_cell: keeps a validated policy and the evaluator that borrows it in one value, so a snapshot can be shared between threads (#42). Its own unsafe is what makes the self-reference sound; this crate stays forbid(unsafe_code).
  • smallvec: inline vectors on the decision path, so a decision does not allocate (#42). Already in the lock file through the server’s dependencies.
  • Dev-dependencies: boon checks documents against the JSON Schema, proptest drives the property tests, criterion runs the benchmarks, hdrhistogram records the percentiles of the budget test, toml reads perf-budget.toml, allocation-counter counts allocations in the zero-allocation test, and insta compares the decision snapshots.
