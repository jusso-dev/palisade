Expand description

The unknown-application policy (#39). Every field is optional in a document; the defaults block every unknown object.

Fields§

§preset: Option<CompliancePreset>

The compliance preset this policy started from, if any.

§default: Level

The level when no entry below applies. The default is block.

§by_location: BTreeMap<LocationClass, Level>

The level per location class.

§by_origin: BTreeMap<OriginClass, Level>

The level per origin.

§by_type: BTreeMap<ObjectType, Level>

The level per object type. restrict only for executables, scripts and installers; prompt not for libraries or drivers.

§restrict_profile: Option<ContainmentProfileRef>

The containment profile of the restrict level (#14). Required when any level, or the prompt’s fallback, is restrict.

§prompt: PromptSettings

How the prompt level asks.

§effects: Effects

Logging, upload, notification, severity and tags of unknown-object decisions (#34). log must be always or sampled: an unhandled object is always reported.

§allow_request: bool

When an unknown object is blocked, the user may ask for approval (#11).

§preexisting_policy: PreexistingPolicy

What happens to files present at install.

§driver_boot_policy: DriverBootPolicy

How unknown drivers are handled during early boot.

§scopes: Vec<Scope>

Where these settings apply, besides the policy’s scope (#38): a subject in at least one of these scopes, at most 1000. Empty, the default, means wherever the policy applies. A subject outside it is decided by the built-in implicit deny (crate::unknown).

§scope_limits: Vec<ScopeLimit>

Effective policies only (#37): where these settings apply, one ScopeLimit per contributing policy, kept as that policy wrote it. The settings apply to a subject when any entry holds; empty, the default, means no further limit. An effective policy has no policy.scope, so the hierarchy moves each contributing policy’s scope and scopes here unexpanded (UnknownPolicy::scope_limit_of). The size is therefore linear in contributing policies, at most MAX_CONTRIBUTING_POLICIES (in hierarchy::limits) entries, and building an effective policy from valid policies never fails on it. Validation rejects it in a document it validates as authored, which writes policy.scope and unknown.scopes instead.

pub fn preset(preset: CompliancePreset) -> Self

The configuration a compliance preset sets, tagged with the preset. Every other field has its default.

  • e8_ml1: default: detect, and block for user_profile, temp and user_writable_other.
  • e8_ml2: default: block.
  • e8_ml3: default: block, and block for driver. Validation also requires a mandatory blocklist. Early-boot drivers are exempt: driver_boot_policy stays audit, so a driver the device loads before the agent has fully started is reported, not blocked, because blocking an unrecognised boot-start driver can leave the device unable to boot (ADR 0018). Validation warns (compliance_weakened) while the exemption is in place; set driver_boot_policy: enforce to close it.

pub fn stricter(&self, other: &Self) -> Self

The strictest combination of self and other, for building an effective policy from several layers (#37).

The goal is the applied level: in every context (object type, location classes, origins, whether the session is interactive, whether containment is available, whether a blocklist rule matched), the merged policy applies a level at least as strict as the level each side applies there with its own prompt fallback and containment profile, and the prompt’s timeout ends no weaker. A level is compared as stage 6 applies it (crate::unknown): a prompt that cannot be shown is its side’s fallback, and a restrict that cannot contain is block.

One policy cannot always reproduce the strictest of two exactly, so where it cannot, the merged policy is the stricter. Three cases, all failing closed:

  • The prompt fallback is one setting for the whole policy, so it is the strictest fallback of the sides that prompt anywhere, and at least detect if the merged policy prompts and either side detects anywhere.
  • Where a side prompts and falls back to block, a merged restrict becomes block unless that side’s own entry there is restrict or stricter: the side blocks wherever no prompt can be shown, and a restrict there would let the object run. Whether a prompt can be shown depends on the session, which a static merge cannot see, so the restrict becomes block everywhere, including where the prompt could have been shown: with A {default: allow} and B {default: restrict, by_origin: {internet: prompt}, prompt.fallback: block}, an internet script in a console session is blocked, though A allows it and B would ask. A merge that carries a condition per entry would be exact.
  • Entries are merged key by key: an entry only one side sets is compared with the other side’s default, even for an object that another entry of that side decides. So when one side matches an object by one dimension and the other side by another, the merge can block what each side alone only detects. With A {default: block, by_type: {executable: detect}} and B {default: detect, by_location: {temp: detect}}, each detects an executable in temp, but the merged temp entry is block (B’s detect against A’s block default), so the merged policy blocks it. Expressing each side’s decision exactly would need entries keyed by type, location and origin together.

How each part merges:

  • default and each entry: the more restrictive level, after each side’s levels are replaced with what that side applies wherever the context does not matter (an entry only one side sets is compared with the other side’s default). So a prompt for a library or driver counts as that side’s own fallback, a restrict for a type that cannot be contained, or without a containment profile, as block, and a prompt fallback as block. No assumption is made that an unusable level ends in block;
  • the prompt: only the answers both sides offer (or block), a justification if either asks, the stronger re-authentication, a user scope if either uses it, and the shorter temporary approval;
  • allow_request only if both allow it; the stricter preexisting_policy and driver_boot_policy; the more demanding compliance preset; where the settings apply: anywhere either side’s limit holds, as scope_limits (everywhere if either side has no limit);
  • effects: per flag, the nearer layer’s value, except that the higher severity and the more immediate upload win, and always logging is kept; tags are joined.

What cannot be compared, the containment profile and the prompt’s timeout and notification wording, comes from self, the nearer layer, where it sets one.

pub fn scope_limit_of( &self, policy_scope: Option<&Scope>, each: impl Fn(Scope) -> Scope, ) -> Option<ScopeLimit>

Where these settings apply, as scope_limits, in an authored policy whose scope is policy_scope: one limit, policy_scope and any of scopes, kept unexpanded. None means everywhere. Each scope is passed through each, which the hierarchy uses to drop options that only act on a deciding rule.

The policy’s own scope_limits are not read: they belong to effective policies, which validation rejects as authored input, so every contributing policy yields at most one limit, of at most one all_of scope and its own scopes. That is what keeps an effective policy linear in contributing policies, and within the authored limits per entry.
