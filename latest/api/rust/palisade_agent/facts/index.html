The bridge from a file’s identity to the facts policy evaluates (#318, #328).

from_identity turns a palisade_fileid [FileIdentity] into the ObjectFacts palisade_policy evaluates, and says which fact classes the record covered (Bridged::computed), so the engine asks for the rest (palisade_policy::engine::Request::computed).

It lives in the agent, not in palisade-policy: policy may depend on palisade-fileid by ADR 0003, but fileid’s graph reaches windows-sys (through ring on Arm64 Windows, and through its optional os-trust feature in a workspace build), which cargo xtask check-deps bans from policy’s graph. The agent already depends on both.

§Fail closed (ADR 0018)

A fact the record does not hold, or holds only as a reason ([Field::NotRequested], [Field::Unavailable] and so on), is absent, so every criterion on it is unknown: never a match, never a mismatch. The mapping never invents a value, and removing a fact from the record only ever removes facts here (tests/facts.rs checks this as a property: no decision becomes more permissive). In particular:

  • Signers. The list is set only when it is complete: every embedded signature was read (fewer than the reader’s limit) and the catalog lookup could show which catalogs list the file. An incomplete list is None, not a shorter list, because a negated signer test on a shorter list could match. A signature is trusted (valid, valid_expired_timestamped, catalog_signed) only when fileid counts it usable: its signer is trusted, its validity checks passed, and neither its digests nor a catalog match rely on SHA-1. A revoked signer or file is revoked, an expired one expired; any other signature that verifies but does not vouch is untrusted_root. A signature that does not verify at all (not even a digest mismatch) is untrusted_root with no facts: its certificates are not bound to it, so nothing it names is known.

  • Paths. The path is the opened file’s final path, never the name as written (which a link may point elsewhere), and never a claimed name hint. A path in a case-sensitive directory is absent. One on a volume whose case folding is not known to be the standard table is kept with PathFact::fold_unknown set (#399), so a path test on it is unknown whenever its result would relax a rule. Its volume is fixed only for fileid’s os_volume and other_fixed; a RAM disk, virtual disk or unknown volume has no volume kind, so a path on it is never trusted (PathFact::acl_proven). It counts as user-writable when a non-administrator can write it or change its permissions.

  • Hashes. The Authenticode hashes are used only when the image’s layout conforms; otherwise they are a best effort, and the flat hash is the identity.

  • Text facts that fileid reports as unknown (a drive type, or a bus it could not name) are absent.

  • Content types (meta.detected_type, meta.extension_type, #376) come from fileid’s classification. What the name claims, and a kind the name helped decide, are used only when the name fileid read is the opened file’s final name.

Not filled here: the location classes (the engine derives them from the path and its volume), the origin (#115, #118) and the path’s alias (the OS final path of a network file is already its UNC form).

§Where the agent calls it

The execution path is not wired yet: no subsystem receives an execution event and decides it (the event sources are #58 and #59, enforcement is #113). This is its seam: it identifies the file with palisade_fileid, calls from_identity, builds the request with Bridged::request (adding the file key and session for the decision cache), and passes it to crate::policy_cache::Active::evaluate. On NeedFacts it runs the tiers that compute the named classes (hashes: hash; signers and metadata: trust, classify and deep; path ACL: context), merges, bridges and asks again.
