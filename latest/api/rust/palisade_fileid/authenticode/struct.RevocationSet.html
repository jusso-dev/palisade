Expand description

Every piece of revocation information the caller has: offline entries from policy, revoked file hashes, parsed CRLs and parsed OCSP responses.

Fields§

§mode: RevocationMode

The mode the caller fetched under.

§failure: RevocationFailure

What to do when an answer is missing.

§unavailable_urls: Vec<String>

CRL distribution point and OCSP URLs whose fetch the caller attempted and could not complete. A certificate that names one of these has an unknown status.

pub fn state_of( &self, chain: &[&CertSummary], index: usize, now: i64, ) -> CertRevocation

The revocation state of chain[index] at time now, where chain is a full chain leaf first, each certificate issued by the next (as super::ChainReport::full_chain_certs gives it). Offline entries are checked first, then CRLs whose signature verifies with the key of chain[index + 1], then OCSP responses that name the certificate under that issuer and that it, or a responder it delegated to, signed. A delegated responder must have been valid at producedAt and must not be revoked by this set (an offline entry, the issuer’s verified CRL, or the issuer’s own OCSP answer); its good answers, and any of its answers as coverage, count only inside its own notBefore to notAfter. An entry in any such CRL, or a revoked OCSP answer, counts, however old; but only a CRL or an OCSP answer (good or revoked) current at now (thisUpdate <= now <= nextUpdate, with nextUpdate present) is an answer that covers the certificate. At most MAX_CRL_CHECKS CRL and OCSP signatures are verified per call.
