The Authenticode PE image hash (#47).

The Authenticode hash identifies a PE image independently of its embedded signature. It covers every byte of the file except three regions:

  1. the 4-byte CheckSum field of the optional header;
  2. the 8-byte certificate table (security) entry in the data directories;
  3. the certificate table itself, located by that entry.

So the hash stays the same when a file is signed, re-signed or has its signature stripped, and any other byte change changes it.

§How the bytes are chosen

HashRanges::from_pe turns a PeInfo from crate::pe::parse into the list of file ranges to hash: the whole file in file order, minus the three regions above. It reuses the parser’s certificate table location, so a table the parser rejected is never excluded. RangeHasher then streams the file through those ranges in a single pass.

The Authenticode specification describes the hash section by section: the headers up to SizeOfHeaders, then each section’s raw data sorted by PointerToRawData (skipping sections with no raw data), then any data after the last section up to the certificate table. For a conformant image, where the sections follow the headers and each other with no gaps or overlaps and the certificate table is the last thing in the file, that is exactly “every byte before the certificate table, in file order, minus the two header fields”. HashRanges::from_pe checks that layout and reports any departure as AuthenticodeStatus::NonConformant.

For a non-conformant image the specification’s steps either read bytes twice, skip bytes, or read past the end of the file, and implementations disagree. The digest returned is then a best effort that still covers every byte outside the three regions. The OS treats such files by their flat hash, so policy must too (#55).

§What the hash does not cover

Because the certificate table is excluded, bytes stored inside it can be changed without changing the Authenticode hash. Signature verification (super::verify_pe, #48) checks the WIN_CERTIFICATE entries and flags hidden data between and after them; anything else in the table is not part of the file’s identity. Rules that must cover every byte use the flat hash.

§Padding

A signer pads an image with zero bytes to a multiple of 8 before it appends the certificate table, because the table must start on an 8-byte boundary. Those padding bytes are part of the signed file and are hashed. When an image has no certificate table and its length is not a multiple of 8, the hash therefore includes the same zero padding (1 to 7 bytes) after the last byte, so the digest equals the one the image will have once signed. One consequence: an unsigned image and the same image with those zero bytes actually appended have the same Authenticode digest. Their flat hashes differ.

§Algorithms

authenticode_hashes always computes SHA-256 and SHA-1, and any other algorithm in the set it is given. SHA-1 (and MD5) are not collision resistant and exist only to match older signatures and OS policy rules; they must never be the sole basis of an allow decision (ADR 0008).

§Page hashes and files on disk

authenticode_hashes also builds the page hash tables (super::page) in the same pass. RangeHasher takes a file’s bytes in order, so a reader can feed one buffer to it, to a super::PageHasher and to the flat-hash MultiHasher at once; super::hash_image_file does that for a file on disk, in one sequential read.
