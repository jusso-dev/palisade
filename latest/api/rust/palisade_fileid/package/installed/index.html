Installed packages (#333): the model the Windows backend fills, mapping an executable to the installed package that owns it, and resolving an app execution alias against it.

Everything here is pure, so it is tested on every OS. The OS reads (enumerating packages, their install folders and manifests) are in palisade_fileid::win::packages, behind the os-trust feature.

§Trust

An InstalledPackage is only as good as its source. The Windows backend fills the identity from the OS’s own package records, not from anything a user can write, and reads the applications from the installed manifest. An install folder is a claim about where the package’s files live: an executable is mapped to a package only when its final path (links resolved) is inside that folder, compared through crate::fsctx::NormalizedPath::starts_with, so a junction or a case-sensitive folder cannot make another file look like the package’s.

An app execution alias (crate::fsctx::reparse::AppExecLink) is entirely its creator’s claim. resolve_alias accepts it only when every claim checks out against the installed packages: a package of that family is installed, the app user model ID names that family and one of its applications, and the target path is that application’s executable inside the package’s install folder. Anything else is an AliasError, never a guess (ADR 0018).
