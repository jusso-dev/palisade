Path normalisation: one canonical form for every way of naming a file.

A file on Windows can be named in many ways (threat model T-engine-04, AT-04): C:\Dir\File.exe, c:/dir/file.exe., \\?\C:\Dir\File.exe, \\.\C:\Dir\..\Dir\File.exe, \??\C:\Dir\File.exe, \\?\GLOBALROOT\Device\HarddiskVolume3\Dir\File.exe, C:\Dir\File.exe::$DATA, C:\DIR~1\FILE.EXE and so on. Path rules must see one form, so a file cannot dodge a rule, or match another rule, by being named differently.

normalize_win32 takes a path as a Win32 API receives it, and normalize_nt takes an NT object path as the kernel reports it (\Device\HarddiskVolume3\...). Both return a NormalizedPath: a Root (drive, UNC share, volume GUID, NT device or other DOS device), the components, and an optional named stream. Nothing here touches the file system or depends on the host OS.

§What Win32 normalisation does

Unless a path starts exactly with \\?\ or \??\, the Win32 layer rewrites it before the kernel sees it, and so does this module:

  • / becomes \, and runs of separators collapse to one;
  • . components are removed, and .. removes the previous component, but never the drive (C:\) or the UNC server and share. In a \\.\ device path nothing is protected, so .. can remove the device itself;
  • a component followed by a separator loses one trailing .. One that ends with two or more dots is rejected, because sources disagree on how many the Win32 layer removes;
  • unless the path ends with a separator, the last component loses all trailing dots and spaces (file.exe. . is file.exe);
  • a reserved DOS device name (CON, NUL, COM1, LPT1, CONIN$ and so on, with any extension) as the last component of a drive path names a device, not a file. Windows versions disagree about this, so such a path is rejected (PathError::ReservedDeviceName).

A path that starts exactly with \\?\ or \??\ skips all of that and is taken literally: \\?\C:\Dir\file.exe. names a file whose name really ends with a dot, a different file from C:\Dir\file.exe. Literal . and .. components, and empty ones, cannot name a file, so they are rejected.

Relative and drive-relative paths (dir\file, \dir\file, C:file) depend on per-process state, so they are rejected (PathError::NotFullyQualified).

§Streams

file.txt:evil.exe names the stream evil.exe of file.txt, and the stream is part of the normalised path (NormalizedPath::stream), so a rule for file.txt does not match it. file::$DATA is the file itself and normalises to file. dir::$INDEX_ALLOCATION and dir:$I30:$INDEX_ALLOCATION are the directory itself, anywhere in the path, and normalise to dir. Both rewrites are recorded in PathNotes.

§Case

NTFS compares names by upper-casing each UTF-16 code unit with the volume’s upcase table. NormalizedPath::case_folded does the same with Unicode simple upper-case mappings, limited to mappings that keep one UTF-16 code unit (so ß stays ß, as on NTFS). The volume’s own table can differ for some non-ASCII letters; it is authoritative and reading it is left to the OS backend (#54). Unicode normalisation (NFC/NFD) is not applied, because NTFS does not apply it either: the two forms are two different files.

A directory can be marked case-sensitive, and then two names that differ only in case are two entries. A parsed path cannot know that, so until NormalizedPath::resolve_case_sensitivity has read each directory’s flag through a CaseSensitivityResolver (the Windows backend’s is palisade_fileid::win::volume::OsCaseSensitivity, applied to every final path it reads), every component is folded. Once read, a component in a case-sensitive directory, or one whose flag could not be read, gets no NormalizedPath::match_key (PathError::CaseSensitiveDirectory), so a rule about it is unknown rather than matched by a folded spelling, and NormalizedPath::starts_with (and so path-variable matching) compares it exactly (#332).

§8.3 short names

A short name such as PROGRA~1 names the same entry as its long name, so a rule must never be matched against it (AT-04.5). A component that could be a generated short name (8.3 shape with a ~) is recorded as a candidate, and NormalizedPath::match_key refuses to produce a key until every candidate has been expanded through a ShortNameResolver, which is the OS hook. A long name can legitimately contain ~; the resolver then returns it unchanged. Paths from the OS’s normalised final path (GetFinalPathNameByHandleW) contain only long names.

Short names that an administrator sets by hand need not contain ~; that is an administrator action and out of scope.

§A string is a name, not an object

A drive letter is looked up in the DOS device map of the logon session that opens the path, and a standard user can add their own (subst, DefineDosDevice). Junctions, symbolic links, mount points and hard links give one file more names. So a normalised string says what a path says, not which file it opens. Decisions about a file use the final path of the opened handle, normalised here (threat model T-agent-13, AT-04.2, AT-04.3). Mapping NT device names, volume GUIDs and drive letters to one volume identity, and mapped drives and DFS paths to their targets, needs the OS and is left to the OS backend (#54).
