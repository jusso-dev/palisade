DFS namespace resolution (#54): a path in a DFS namespace (\\domain\dfs\apps\tool.exe) names a file on a target share (\\server\apps\tool.exe), and rules about the file should match either.

The lookup itself is the OS’s (palisade_fileid::win::paths::OsDfs) and can block on the network for a long time, so it goes through a DfsResolver and a DfsCache that:

  • gives up after a timeout (DEFAULT_TIMEOUT, 2 s, as #54 asks). A lookup that times out keeps running on its own thread, so at most DfsCache::max_in_flight such threads exist at once; past that, a new lookup is reported as timed out without starting;
  • caches referrals for DfsCache::ttl, and “not DFS”, timeouts and failures for DfsCache::negative_ttl;
  • follows a target that is itself in a namespace up to MAX_HOPS times.

What a cached answer may stand for is limited, so two spellings of one file never resolve differently because of what was asked first:

  • A link referral (\\domain\dfs\apps) answers for every path under its entry: DFS does not allow a link below another link in one namespace. A link whose target is another namespace is a further hop.
  • A root referral (\\domain\dfs itself) answers only for the path that was looked up. Links live below the root, so a cached root must not stand in for an unseen descendant, which may be under a link.
  • “Not DFS” is cached for the path that was looked up, never for its share: one path outside every link says nothing about another path on the same share. No resolver gives share-wide evidence today. So each new file reached through a link costs one lookup of its target path, to see that the target is final.
  • A timeout or failure is cached for the whole share, so a slow or dead server is not asked again on every file.

A timeout or failure is reported as such, never as “not DFS”: a caller must not treat an unresolved namespace path as matching no rule.
