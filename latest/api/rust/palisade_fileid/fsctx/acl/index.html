Security descriptors, ownership and the writability decision.

The OS layer reads a file’s security descriptor (owner and DACL) as the self-relative bytes GetSecurityInfo / GetFileSecurityW return, and SecurityDescriptor::from_self_relative turns them into an abstract model. Everything after that is pure and runs on every OS:

  • evaluate works out which write-type rights any non-administrator principal may hold on one object;
  • assess_path does that for a file and every ancestor folder up to the volume root and produces a Writability summary;
  • OwnerInfo classifies the owner SID.

§How the evaluation works

The DACL is walked in stored order, as the OS access check does (a non-canonical order is evaluated as stored and also reported). For a token, each applicable ACE whose SID is in the token either grants the bits not already denied, or denies the bits not already granted. ACEs marked inherit-only apply only to future children and are skipped; inherited ACEs are already materialised in the DACL and count like any other.

The DACL is indexed by trustee once per descriptor: for each SID, the first applicable ACE that grants or denies each right. A token’s rights are then the earliest entry among its SIDs, right by right, which is what the ordered walk gives, without walking the DACL once per token (#332). A property test checks the index against the ordered walk.

The tokens evaluated are:

  • one per distinct non-administrator SID named by an applicable allow ACE, holding that SID plus Everyone. This over-approximates every real non-administrator token that holds Everyone: take the first allow ACE that grants a right to a real token. No deny ACE before it applied to the real token, so none applied to the smaller token of that ACE’s SID either, and that token is granted the right too. An anonymous token lacks Everyone by default and may hold ANONYMOUS LOGON and NETWORK, so ANONYMOUS LOGON is evaluated alone, and NETWORK both alone and with Everyone. A deny for Everyone is then not assumed to stop either;
  • the object’s owner, if it is not an administrator, with the owner’s implicit READ_CONTROL and WRITE_DAC (which a deny ACE cannot remove), unless the DACL has an unconditional OWNER RIGHTS allow ACE, which then replaces them. A descriptor with no owner is treated as an unknown, possibly non-administrator owner;
  • a synthetic standard user (by default Everyone, Authenticated Users, BUILTIN\Users, INTERACTIVE and LOCAL), reported on its own.

§Conservative by construction

When the model cannot tell, it reports the right as possibly held:

  • Conditional (callback) allow ACEs and object allow ACEs may apply; their rights are reported, and also listed as uncertain. Conditional and object deny ACEs are assumed not to apply when working out what may be held. They are assumed to apply when working out what is held for certain, so a right that such a deny may remove is uncertain, not certain.
  • Generic rights (GENERIC_WRITE, GENERIC_ALL) in an allow ACE are mapped to the file rights they stand for. The OS access check does not map generic bits stored in an ACE, so such an ACE may in fact grant nothing; mapping it can only over-report, and a right that only a generic bit grants is uncertain. In a deny ACE they are not mapped, so they deny nothing, as in the OS.
  • ACE types the model does not know grant every right, as uncertain, to an unknown principal.
  • A NULL or absent DACL grants everyone everything.
  • An object whose descriptor could not be read counts as writable.
  • Mandatory integrity labels (in the SACL) are ignored. A label can only take rights away, so ignoring it only over-reports.

On Windows the OS access check (AuthzAccessCheck with a synthetic token of the standard user’s SIDs) runs beside this evaluator, and a decision uses the union of the two (OsCheck, ObjectWritability::merge_os_check, #332): the OS check is exact but covers only the standard user, while this evaluator covers every non-administrator principal and over-reports. So the OS check can add a right the evaluator missed, never remove one it reports, and if the OS check fails the evaluator’s result stands (ADR 0018). palisade_fileid::win::access::assess_file merges it in, and cross_check_writability reports both on any descriptor (with the os-trust feature).

§Owner-based trust needs the DACL too

NTFS keeps a file’s owner when its content is overwritten in place; the owner only changes when a new file is created. So an administrator owner says nothing about the content if a non-administrator can write to the file (threat model T-engine-11, AT-19.5b). Writability::owner_trust_blockers reports the rights (write, append, delete, WRITE_DAC, WRITE_OWNER) that must be absent before owner-based trust (#117) may rely on the owner. This module only provides the attributes; the trust decision is #9’s.
