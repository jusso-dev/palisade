Script signature blocks (#52): the embedded Authenticode signatures of PowerShell, VBScript, JScript and Windows Script Files, and the signed metadata attributes that give such files version-like identity.

A signed script carries its PKCS#7 SignedData as base64 in comment lines at the end of the text (for a Windows Script File, in a <signature> element before the last </job>). The SignedData is the same Authenticode structure a PE file carries, except that its indirect data is SPC_SIPINFO (1.3.6.1.4.1.311.2.1.30), naming the subject interface package (SIP) that hashed the text, and its digest is that package’s digest of the script.

  • verify_script finds and checks the block, computes the digest the way the OS package does, and verifies the signature with the same machinery as PE signatures (#48): the strict DER reader, the SignedData decoder, the signer certificate lookup, the messageDigest check and the signature over the authenticated attributes. The result is a ScriptReport, whose ScriptReport::signatures holds at most one SignatureKind::Script signature that crate::authenticode::evaluate_trust and crate::authenticode::evaluate_validity take like any other.
  • evaluate_script_trust decides trust under a ScriptAnchorPolicy: the OS requires a script’s root to be in the machine root store, unlike a PE file’s.
  • crate::authenticode::SignedMetadata holds the signed metadata attributes (1.3.6.1.4.1.311.2.7.1 to .10). They are read from every signature, PE ones included, into crate::authenticode::SignerAttributes::signed_metadata.

§The digest

Both kinds of package hash the script as UTF-16LE text, without the signature block and the line break before it:

PackageFormatsByte order markAppended
PowerShell.ps1 .psm1 .psd1, .ps1xml .psc1 .cdxml, .mofhashed, as U+FEFFnothing
Windows Script Host.vbs, .js, .wsfnot hashedthe block’s position, in UTF-16 units of the hashed text, as a 32-bit little-endian integer

For .wsf, the text after the block (the closing </job>) is hashed too. The text is decoded by its byte order mark: UTF-8, UTF-16LE or UTF-16BE (the PowerShell package does not sign UTF-16BE). Line endings (CRLF, LF or a lone CR) are hashed as they are: an LF file and a CRLF file have different digests. These rules are checked against scripts signed by OS tooling in every format, encoding and line-ending combination, against signed scripts the OS ships, and on Windows CI against the OS’s own verdict on every fixture (tests/script.rs).

One case has no defined digest: UTF-8 text with a character outside ASCII in a script host format. The OS’s own signer signs it, and the OS’s own verifier then reports a hash mismatch, so no rule both agree on exists. Such text is TextIssue::NonAsciiUtf8, never valid. UTF-8 text that is all ASCII, and UTF-16 text, are read as above.

§Failing conservative

A script’s signature is untrusted input, and interpreters read text in more ways than one. So anything ambiguous, truncated or lossy fails the check, and never makes a file look signed:

  • Text without a byte order mark is decoded by the OS from a guess, falling back to the machine’s code page, so its digest depends on the machine. It is read only when it is ASCII without NUL, which every candidate decodes the same way; otherwise TextIssue.
  • Invalid UTF-8 after a UTF-8 byte order mark, unpaired surrogates or an odd length in UTF-16 text, a UTF-32 byte order mark, UTF-16BE PowerShell text, and non-ASCII UTF-8 script host text are TextIssues too.
  • The block must be exactly as signers write it: one begin line and one end line, each a whole line; a CRLF before the begin line; every line ending in CRLF; every data line the format’s comment prefix, strict base64 and the comment suffix; and nothing after the end line except, for .wsf, the rest of the file, which must hold a </job> (the block sits inside a job). Anything else is a BlockError. The exact marker text anywhere else in the file, even inside a string, is one too (BlockError::MultipleBlocks), because another reader could take it for the block. Marker text that differs from the format’s in case or spacing is not marker text, so such a file is unsigned.
  • The base64 must decode to exactly one DER SignedData whose SpcSipInfo names the format’s package. Nested signatures are checked as DER but not verified (ScriptWarning::NestedSignaturesIgnored).
  • Encoded scripts (.vbe, .jse) are not read at all: they are unsigned, with ScriptWarning::UnsupportedEncoding.
  • Files over ScriptOptions::max_size are not read: ScriptSigningState::TooLargeForSignatureCheck.

§Not done here yet

  • Reading the OS machine root store, and the OS trust-verification cross-check, need the Windows API (os-trust, #48 and #95). The caller supplies the root store as a TrustConfig.
  • Catalog-signed scripts: ScriptReport::catalog_digests is the hook for a crate::catalog::CatalogStore lookup; matching against catalogs made by OS tooling, and folding a match into the file’s signing state, are #51 and #55.
  • Feeding the signed metadata into the unified file identity record is #55; interpreter enforcement is #92 to #95.

Functions§

evaluate_script_trust
Builds the chain of report’s signature against the anchor sets policy allows, and decides whether its signer is trusted. Only a ScriptSigningState::Valid script is ever trusted; check ScriptReport::signing_state for why another is not, since its ScriptReport::signatures holds no signature when the block itself could not be read (its state is then crate::authenticode::InvalidReason::ScriptSignatureBlock). Expiry, timestamps and revocation are crate::authenticode::evaluate_validity, with ScriptReport::signatures and ScriptTrust::trust.
verify_script
Reads the script data as kind and checks its signature block.
verify_script_file
Reads the script at path as kind, within ScriptOptions::max_size (a larger file is not read), and checks its signature block. Fails with std::io::ErrorKind::InvalidInput for anything but a regular file, without blocking on a FIFO. An encoded script is not read at all.
