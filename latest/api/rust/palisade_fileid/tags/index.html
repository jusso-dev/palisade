Content tagging (#44, feature content-rules).

scan looks for byte patterns in a file and attaches string tags such as installer:scripted-setup or archive:embedded-pe. Tags come from two rule sets:

  • The built-in set (BUILTIN_TAGS), which is read-only. It recognises common installer engines, self-extracting archives, embedded executables and archives, compiled scripts and the standard anti-malware test file. Its tags cannot be redefined.
  • The organisation’s rules (RuleSetSource), carried in policy. A rule is a list of masked byte patterns (hex with nibble wildcards, text or wide text), each with a location (anywhere, at an offset, in a range, in a PE image’s appended data or in the file’s tail), and a condition (any, all, or at least N of them).

§A pattern language, not a rule engine

The rules are deliberately less expressive than a general pattern rule language: no regular expressions, no gaps of variable length, no loops, no arithmetic over the file and no modules. Every pattern has a fixed length of at most MAX_PATTERN_LEN bytes, so checking it costs at most that many comparisons. Patterns that are not at a fixed offset are found through their longest exact run of bytes (an “atom”, at least MIN_ATOM_LEN bytes) with one multi-pattern automaton (aho-corasick), in a single linear pass. So a scan’s cost is linear in the bytes scanned plus the candidate checks, and both are capped by ScanLimits.

The rule format can be targeted by a front end for a general rule syntax later. A YARA-syntax front end through the yara-x crate was considered and not adopted: every release from 1.22 needs a newer Rust than the workspace’s minimum (1.94), and the last one that builds on 1.94 brings in a WebAssembly compiler and about 110 more crates, with 37 build scripts (one generating code at build time), and takes the workspace from 8 to 22 crates in more than one version, over the limit of 10 (docs/dependencies.md).

§Never a stall, never an error

Tagging must not hold up identity, so a scan has a hard budget:

  • Files larger than ScanLimits::max_file_size (32 MiB by default) are scanned in part: the first max_file_size bytes and the last TAIL_SCAN_LEN. The report then has CONTENT_SCAN_PARTIAL.
  • Scanning stops once ScanLimits::max_scan_bytes bytes have been read, ScanLimits::max_match_steps pattern comparisons have been made, or ScanLimits::timeout (2 s by default) has passed. The report then has CONTENT_SCAN_TIMEOUT.
  • A read error, or a file that ends before the length its reader reported (truncated while being scanned), ends the scan with CONTENT_SCAN_ERROR. Bytes that did arrive in a chunk are scanned first. A short read of the start-of-file filter or the PE headers stops at once, because what they decide could not be established.
  • A rule’s unless_start filter is checked before anything else, and a filter that could not be checked counts as matched, so a budget or a size limit can never let a filtered rule through.

None of these is an error: scan always returns a TagReport. Tags found before the scan stopped are kept, because each is positive evidence on its own. A missing tag is never evidence of absence when the report has a status tag. Callers should treat such a file as not fully inspected and fail conservative: a rule that requires a tag should not be satisfied by its absence.

The scan runs in the calling thread and is cooperative: the time limit is checked before every read, between chunks, every few thousand candidate checks, on each retry of an interrupted read and after the last chunk, but it cannot interrupt a read or seek that blocks. A scan of a reader that blocks can therefore outlast timeout. Running it off the identity hot path, in a separate worker that can be abandoned, is the caller’s job. That worker is not part of this crate and is not built yet: the agent’s file pipeline (#4, #59, #60) will provide it, with its scheduling, queueing and cancellation.

The file is read more than once: the start-of-file filters and the PE headers are read first, then the file is read again in chunks. A file rewritten at the same length between those reads can be judged on a mix of its two versions (a filter decided on the first, strings on the second), and the scan still reports ScanStatus::Complete. Callers that need one consistent view should scan a snapshot, or a file they hold open with writes denied, as the agent does for hashing.

§Rule sets in policy

A RuleSetSource is plain data (serde). It has a version, and ContentRules::rules_digest is a SHA-256 over a canonical encoding of it, so the policy bundle (#43) can record exactly which rules were in force. The encoding covers the version and every rule as written, with only the pattern bytes normalised (hex case and spacing); see ContentRules::rules_digest for what equal digests mean. The rule set has no signature of its own: it is part of the policy bundle, whose signature (#225) covers it.

A bundle bootstrapper that chains installer packages: a PE image with the bootstrapper’s 8-byte section name anywhere a section table can be, and the bootstrapper’s section header (magic 0x00F14300, version 2) anywhere in the file. The two are found independently: the rule does not resolve the named section or check that the header is at its raw data, so it is a two-marker heuristic.
INSTALLER_MSI_WRAPPER

The two are found independently: the rule does not check that the CLSID is the root entry of that compound file, so a PE that holds some other compound file and the same 16 bytes elsewhere is tagged too. Installer wrappers and bootstrappers that unpack and run an MSI look like this.
