File stamps: what identifies one version of one file, for the hash cache (#46).

A cached digest may be reused only while the file is provably the same file, unchanged. On a volume with a change journal that is the strong key: volume serial, 128-bit file ID, the journal’s ID, the file’s last USN, last-write time and size. Any write moves the USN, so a match means the content is the one that was hashed. The journal ID is part of the key because a deleted and recreated journal restarts its USNs, so an old USN could otherwise come round again.

A rename also moves the file’s USN, so on its own it is a miss (which fails safe: the file is hashed again). The journal consumer (#60), which can see that every journal record since the cached USN is a rename and nothing else, may carry the entry over: it finds the cached key with super::HashCache::key_of and calls super::HashCache::rekey_after_rename.

Without a journal (FAT, exFAT, ReFS without one, network shares) the key falls back to the normalised path, size, last-write and creation times. Timestamps can be set by anyone who can write the file, so such a key is weak (FileKey::is_weak), and the verify mode can refuse to trust it (super::cache::HashVerifyMode).

Reading these values needs OS calls (GetFileInformationByHandleEx with FileIdInfo, FSCTL_QUERY_USN_JOURNAL and FSCTL_READ_FILE_USN_DATA). The Windows backend, palisade_fileid::win::file::WinStamps (with the os-trust feature), implements FileStamp with them. This module only defines the types, so the cache logic is portable and tested everywhere.
