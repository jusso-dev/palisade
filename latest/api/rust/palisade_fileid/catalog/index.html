Catalog-signed files (#51): catalog parsing, catalog signature checks, the catalog store and its member index.

Many OS components and drivers carry no embedded signature. A catalog file (.cat) signs them instead: a PKCS#7 SignedData whose content is a certificate trust list (CTL, szOID_CTL 1.3.6.1.4.1.311.10.1) of member digests. A file is catalog-signed when a catalog whose signature is valid lists its digest, and the catalog’s signer is then the file’s publisher.

  • parse_catalog decodes a catalog file and verifies its signature with the same machinery as embedded Authenticode signatures (#48): the strict DER reader, the SignedData decoder, the signer certificate lookup, the messageDigest check over the CTL and the signature over the authenticated attributes. The result is a Catalog: the decoded CertificateTrustList and a SignatureReport with one SignatureKind::Catalog signature, which crate::authenticode::evaluate_trust takes like any other (#49).
  • parse_ctl decodes a CTL on its own.
  • CatalogStoreBuilder loads catalogs from bytes or from a directory tree, within StoreLimits, into a CatalogStore that indexes, by digest, the members of catalogs whose signature is valid. CatalogStore::lookup takes a file’s FileDigests and returns each catalog that lists it, trusted catalogs first, with the signer’s trust verdict and identity.

§Which members are indexed

Only members of a catalog whose signature is valid, and of those only members with an SPC_INDIRECT_DATA digest under SHA-256 or SHA-1. Members with no digest, or a digest under another algorithm, are kept in the CertificateTrustList but never indexed. Limits can leave out members that would otherwise be indexed: those past MAX_MEMBERS in one catalog (CertificateTrustList::members_truncated) and those past StoreLimits::max_members in the store (CatalogRecord::index_truncated). So a lookup that finds nothing does not show that no catalog lists the file; check those flags, and the store’s records, before treating a miss as absence.

§Member digests

A member’s SPC_INDIRECT_DATA attribute holds its digest and the indirect data type. For a PE member (SPC_PE_IMAGE_DATA) the digest is the Authenticode image hash (#47); for any other file it is the hash the file type’s subject interface package computes, which for files without one is the flat hash (#46). v1 catalogs (szOID_CATALOG_LIST_MEMBER) use SHA-1, v2 catalogs (szOID_CATALOG_LIST_MEMBER2) SHA-256; the index takes whatever algorithm each member names. Members are indexed by digest, never by their tag string or File name, which the signature covers but which say nothing about the file’s content.

SHA-1 members are compatibility-only (ADR 0008): a match reports its algorithm, and policy must not let an allow decision rest on a SHA-1 match alone (#40).

§What a match means

A CatalogMatch says that a catalog whose signature is cryptographically valid lists the file’s digest. Whether its signer is trusted is CatalogMatch::trusted, decided by the TrustConfig given when the catalog was loaded. Catalogs whose signature is not valid (tampered, unsupported, malformed) are recorded with their status but never indexed, so they match nothing.

Given ValidityOptions, the builder also judges each catalog’s signature as of when it was made, with the same machinery as embedded signatures (#50): the catalog’s own timestamps, expiry, revocation of its chain, and revocation of the catalog file by hash. CatalogMatch::usable is true only for a trusted catalog whose signature passed all of it; without validity options no match is usable.

§Settings, the persistent index and authoring

  • CatalogSettings: catalog_lookup_enabled, catalog_scope and skip_catalog_for_paths, applied by CatalogStore::lookup_with and CatalogIndex::lookup_with. A skipped lookup says why, for the log.
  • CatalogIndex: the persistent index. It is built from a store, written with an HMAC-SHA-256 tag (CatalogIndex::encode) and read back only when the tag verifies and it was written by this library version and index format (CatalogIndex::decode; anything else asks for a full rebuild). It is updated in place as catalogs are added, changed or removed (CatalogIndex::remove_path, CatalogIndex::merge), and reports IndexState::Building until its first build is complete, during which a miss is CatalogLookup::Indeterminate, never a “not catalog-signed”.
  • build_catalog: an unsigned catalog definition from a recorded set of files, for organisation catalogs.

§Not done here

  • Watching the catalog directories for changes is the change feed (#60), and scheduling the first build at low priority is #65: both are the agent’s. This module takes their results.
  • The OS catalog database cross-check (CryptCATAdmin*, Windows, os-trust) belongs to the Windows backend (#48).
  • Folding catalog matches into a file’s signing state (CatalogValid) is the unified file identity record (#55).

§Untrusted input

Catalog files are attacker-controlled. The same rules as for embedded signatures apply: DER only, typed errors, no panics, no allocation sized by a declared length, and fixed limits: MAX_CATALOG_SIZE, MAX_MEMBERS, MAX_ATTRIBUTES, MAX_NAME_VALUES, MAX_VALUE_BYTES, MAX_CTL_WARNINGS and MAX_DECODED_BYTES per catalog, and StoreLimits for a store. The trust list is decoded before its signature is checked, so MAX_DECODED_BYTES bounds the memory an unsigned or forged catalog can take. The fuzz_ctl fuzz target covers parsing, loading and lookup.

It is checked as each member and extension is decoded, and before the member list grows, so the overshoot is at most the one member being decoded (itself bounded by the per-member limits).
