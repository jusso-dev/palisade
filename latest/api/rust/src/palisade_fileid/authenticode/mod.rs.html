1//! Authenticode for PE images.
2//!
3//! - [`hash`]: the Authenticode image hash (#47), which identifies a PE file
4//!   independently of its embedded signature.
5//! - [`page`]: page hash tables (#47), built from a file and checked against
6//!   the table a signature carries.
7//! - [`hash_image_file`] and [`hash_image_reader`]: the flat hashes, the
8//!   Authenticode digests and the page hash tables of a file, in one
9//!   sequential read.
10//! - Signature parsing and verification (#48): [`verify_pe`],
11//!   [`verify_signatures`] and [`verify_certificate_table`] read every
12//!   `WIN_CERTIFICATE` entry, decode each PKCS#7 SignedData and its nested
13//!   signatures, and check them. The result is a [`SignatureReport`] with
14//!   one [`SignatureInfo`] per signature, the primary signature and the
15//!   file's [`SigningState`].
16//!
17//! # What "valid" means here
18//!
19//! A signature is [`SignatureStatus::Valid`] when all of these hold:
20//!
21//! 1. it parses as an Authenticode SignedData: content type
22//!    `SPC_INDIRECT_DATA`, a `SPC_PE_IMAGE_DATA` indirect data, exactly one
23//!    SignerInfo with `contentType` and `messageDigest` attributes;
24//! 2. the `messageDigest` attribute equals the hash of the encoded
25//!    `SpcIndirectDataContent`;
26//! 3. a certificate in the blob matches the SignerInfo's signer identifier,
27//!    and the signature over the DER-encoded authenticated attributes
28//!    verifies with its public key;
29//! 4. the image digest in the indirect data equals the file's Authenticode
30//!    digest under the same algorithm;
31//! 5. neither digest is MD2 or MD5;
32//! 6. the image layout conforms to the Authenticode specification (#47).
33//!    On a non-conformant image (data after or a misaligned certificate
34//!    table, gaps or overlaps between sections, and so on) a matching
35//!    digest is reported as [`SignatureStatus::NonConformantImage`], never
36//!    as valid.
37//!
38//! It does **not** mean the signer is trusted.
39//!
40//! # Chains, trust and signer identity (#49)
41//!
42//! - [`CertSummary::from_der`] parses an X.509 certificate into every
43//!   attribute signer rules match on: subject and issuer as ordered RDNs
44//!   with typed components and a canonical DN string, serial, validity,
45//!   algorithms, key size, thumbprints, TBS hashes, key identifiers, basic
46//!   constraints, key usage, EKUs (named from the [`eku`] catalogue),
47//!   policies, CRL and AIA URLs, and whether it is self-signed.
48//! - [`build_chain`] orders a signature's embedded certificates into the
49//!   as-provided chain (leaf, intermediates, PCA, root) and builds the
50//!   full chain against a [`TrustConfig`] of policy-shipped anchors and
51//!   intermediates, verifying every link's signature.
52//! - [`evaluate_trust`] does that for every valid signature in a
53//!   [`SignatureReport`] and picks the primary signature **among trusted
54//!   signers only**, so a nested signature from an untrusted signer can
55//!   never become primary. It yields the [`SignerIdentity`] publisher rules
56//!   use, or, for a file with no trusted signer, an unverified
57//!   [`VendorHint`]. [`SignatureReport::primary`] is the #48 choice by
58//!   cryptographic validity alone; trust decisions must use
59//!   [`TrustReport::primary`].
60//! - [`extract_certificates`] lists the certificates a signed PE image,
61//!   cabinet or PKCS#7 file carries, and [`CertificateBundle`] gathers them
62//!   into a trust bundle.
63//!
64//! # Timestamps, expiry and revocation (#50)
65//!
66//! - [`verify_timestamps`] verifies a signature's RFC 3161 and legacy
67//!   countersignature timestamps against a TSA [`TrustConfig`].
68//! - [`evaluate_validity`] judges every signature as of when it was made:
69//!   the trusted signing time, expiry ([`ExpiryPolicy`], Lifetime Signing),
70//!   revocation data the caller supplies ([`RevocationSet`], [`Crl`],
71//!   [`OcspResponse`]), and per-certificate relaxations. Every outcome is one
72//!   [`VerificationError`] code, shared with the OS event decoder (#58).
73//!   Allow decisions must use [`ValidityReport::primary`].
74//!
75//! # The OS cross-check (#48)
76//!
77//! [`cross_check`] compares a [`SignatureReport`] with what the OS
78//! trust-verification API said about the same file (read by
79//! `palisade_fileid::win::trust` on Windows with the `os-trust` feature)
80//! and records every disagreement as a diagnostic. It never changes the
81//! report. Catalogs are [`crate::catalog`] (#51).
82//!
83//! # Untrusted input
84//!
85//! The certificate table and everything in it is attacker-controlled. The
86//! ASN.1 layer (one module, `asn1.rs`, kept small for audit) accepts DER only, rejects BER indefinite lengths
87//! and oversized or non-minimal lengths with a typed [`Asn1Error`], and
88//! borrows instead of allocating, so no declared length sizes an
89//! allocation. Fixed limits bound the rest: [`MAX_CERTIFICATE_ENTRIES`],
90//! [`MAX_CERTIFICATE_TABLE_SIZE`], [`MAX_NESTING_DEPTH`],
91//! [`MAX_SIGNATURES`], [`MAX_CERTIFICATES`], [`MAX_TIMESTAMPS`] and
92//! [`MAX_WARNINGS`]. Nothing panics.
93//!
94//! # Cryptography
95//!
96//! Signature verification goes through one thin module that wraps `ring`
97//! (ADR 0008). RSA PKCS#1 v1.5 (SHA-1, SHA-256, SHA-384, SHA-512), RSA-PSS
98//! (SHA-256, SHA-384, SHA-512, with MGF1 over the same digest and a salt as
99//! long as it) and ECDSA P-256 and P-384 (SHA-256, SHA-384) are verified.
100//! ECDSA P-521, Ed25519, Ed448 and other combinations are reported as
101//! [`SignatureStatus::Unsupported`], never as valid.
102//!
103//! # OS-native signer rules
104//!
105//! OS code integrity accepts only RSA signers of up to 4096 bits, and no
106//! MD2 or MD5. [`SignatureInfo::os_ci_compatible`] is `false`, with the
107//! reasons in [`SignatureInfo::os_ci_issues`], for any other signer, so a
108//! compiled rule never silently fails.
